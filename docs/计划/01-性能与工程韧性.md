### P-8 首屏拆 `modal-settings` 反向耦合

- **目标**:首屏不再加载 `modal-settings`;弹窗懒加载语义恢复。
  **注**:计划拟定值「少 188,565 B / 61,850 gz」**经实测不成立**——该 chunk 中大部分是被入口共享的模块,
  去掉归组后仍需进首屏(只是改为并入 index chunk),真正可移除的只有弹窗实现本身。
  实测收益:首屏 raw 774,952 → 745,413(−29,539);gzip 271,621 → 260,793(−10,828)。
- **现状证据**(已实测):
  - `web/vite.config.ts:29` 的 `manualChunks` 把 `/components/SettingsHub` 与
    `/components/SettingsModal` 强制归入 `modal-settings`。
  - `web/src/components/SettingsModal.vue:11-17` 静态 import 了 `../store`(useAppStore)、
    三个 composable(`useApiSettings`/`usePromptInject`/`useDataManager`)、两个 section 组件。
  - `web/src/store.ts:21-27` 顶层实例化全部子 store。
  - 结果:被入口与弹窗**共享**的模块落进 `modal-settings`,于是 `index.js` 不得不静态
    import 该 chunk → `index.html` 发出 `modulepreload` → **首屏多拉 188KB / 62KB gz**。
  - vite.config 注释里「避免把首屏共享模块误划入异步 chunk 造成反向耦合」的护栏**没覆盖这条路径**。
  - **2026-09-16 复核**:`web/vite.config.ts:29` 该行仍在;`web/dist/index.html` 仍有
    `modal-settings` 预载;`modal-settings-CQ9DXqUA.js` 仍是 188,635 B → 本批次未启动。
- **改动点**:
  1. **量基线**:`npm run build -w web` 后记录 `dist/index.html` 的 modulepreload 列表与
     各 chunk 体积,追加进 `tools/perf-baseline.json` 的 `_README`(机读)与 `docs/功能-变更史.md`(证据链;作为 P-12 预算与回归对照)。
  2. **主方案**:删除 `manualChunks` 中两条 app-code 归组(`SettingsHub`/`SettingsModal`),
     让 `modals.ts:40` 的动态 `import()` 自然产出异步 chunk。
     8 个 section 已由 `SettingsModal.vue:18-30` 的 `lazyModal` 各自成 chunk,不受影响。
  3. **验证是否真的解开**:重新构建后断言 `dist/index.html` **不含** `modal-settings`,
     且 `index-*.js` 不再出现 `from"./modal-settings-…js"`。
  4. **备选(仅当主方案产生反向耦合或碎片过多时)**:保留归组但对
     `/src/store.ts`、`/src/stores/`、`/src/composables/`、`/src/asyncModal.ts`
     返回固定 chunk 名(如 `'app-core'`),确保 `modal-settings` 内不再含被入口引用的模块。
  5. 复核 `web/src/modals.ts` 注册表在本改动后仍与 `modals.test.ts` 的元测试一致。
- **验收断言**:
  - `npm run build -w web` 通过;`dist/index.html` 无 `modal-settings` 预载;
  - `npm test -w web` 全绿(注意 `modals.test.ts` 可能断言 chunk 归属);
  - **手动**:打开综合设置,逐个 tab 切换,确认 10 个懒加载分区仍正常(SettingsModal.vue:19-28 的 lazyModal 共 10 个,+ 2 个静态);
  - 记录新体积到 `tools/perf-baseline.json` 的 `_README` 与 `docs/功能-变更史.md`。
- **风险 / 回滚**:风险中——`manualChunks` 调整会改变 chunk 划分,可能出现循环 chunk 或某个
  chunk 变大。回滚 = `git revert` 单个 commit(vite.config.ts + 可能的 modals 调整)。
  **注意**:`web/dist` 被 `include_dir!` 编入 server 二进制(`server-rs/build.rs`),
  手动验证前必须重新 `npm run build -w web` 并重建 server,否则服务端仍发旧资源。
- **依赖 / 需确认**:无前置依赖;但 P-12 依赖本批次(顺序不可颠倒)。
- **状态**:**已完成**(2026-09-17,提交 `c532a11`)——首屏预载实测已无 `modal-*`;首屏 raw 774,952 → 745,413、gzip 271,621 → 260,793。**注**:计划拟定收益「少 188,565 B」经实测不成立(该 chunk 多为入口共享模块),详见本节「目标」行的说明

### P-9 虚拟滚动与渲染缓存生命周期对齐

- **目标**:滚动卸载/重挂后不重复计算 markdown/sanitize/脚本渲染;缓存有界不泄漏。
- **现状证据**:
  - `useVirtualMessages.ts:147-154`:离开缓冲区即销毁组件(模板降级为占位 `div`)。
  - `ChatMessageItem.vue:213-234` 的 `html` 是**组件内 computed**,组件卸载即失效;
    其内部 `renderScopedScripts`(`render.ts:377`)与 `renderMarkdown`(`markdown.ts:59`)
    都是无外部缓存的直接调用。
  - 代价参照:`sanitize-html` 处理 16.8k 字符 ≈ 3.057ms(`archive/2026-09-16-consolidation/perf-baseline.md:118`),
    含 HTML 卡片的长会话来回滚动会反复付这份成本。
  - **2026-09-16 复核**:`web/src/renderCache.ts` 不存在;
    `useVirtualMessages.ts` 仍为 `tailKeep ?? 30` / 固定 `overscanPx=1200` → 本批次未启动。
- **改动点**:
  1. **先写失败测试**:加渲染计数(mock 或 spy 统计 `renderMarkdown`/`renderScopedScripts`
     调用次数),断言「同一消息内容二次渲染不重算」。
  2. **缓存提到模块级**:新增 `web/src/renderCache.ts`(或并入现有渲染模块),
     提供有容量上限的 Map(建议容量 500,超出按 FIFO/LRU 淘汰)。
  3. **缓存键沿用现有脚本缓存口径**(`ChatWindow.vue:61-91` 的
     `${scopeId}|${scriptHash}|${depth}|${text}` 形态),并加入 `renderHtml` 开关与
     `scripts` 版本(复用 `props.scriptHash`),保证:
     - 内容变更 → key 变更 → 必 miss(响应式正确);
     - `scripts` 引用或字段变化 → key 变更 → 必 miss(脚本热更新即时生效)。
  4. `ChatMessageItem.vue` 的 `html` computed 改为「先查模块级缓存,未命中再算并写回」,
     命中路径不得触发 `sanitize`。
  5. 顺带收敛 `overscanPx=1200` 固定像素对超高卡片覆盖不足的问题:改为按**条数窗口**
     (建议上下各 8 条)与像素窗口取较大者,减少挂载/卸载抖动。
  6. **不要**把缓存做成全局无界(内存风险);淘汰策略写进注释与测试。
- **验收断言**:
  - `npm test -w web` 全绿,**含新增的缓存命中用例**(证明二次渲染零重算);
  - 长会话(>80 条、含 HTML 卡片)滚动时,Performance 面板无重复 `sanitize-html` 长任务;
  - `npm run typecheck -w web` 与 `node tools/check-frontend-lint.mjs` 通过(类型逃逸只降不升)。
- **风险 / 回滚**:风险中——key 设计错误会渲染**陈旧内容**(显示 bug)。缓解:key 必须包含内容
  本身(或内容哈希),而非仅消息 id;测试覆盖「内容变更必重渲」。
  回滚 = revert 单个 commit(缓存模块 + 组件调用点)。
- **依赖 / 需确认**:无前置依赖。缓存容量取值(建议 500)可在实施时确认。
- **状态**:**已完成**(2026-09-17,提交 `09a9e04`)——新增 `renderCache.ts`(容量 500、FIFO、含统计);`ChatMessageItem`/`ChatWindow` 接入模块级有界缓存;虚拟滚动加条数窗口 `rowWindow`(默认上下各 8 条)
- **来源**:archive/2026-09-16-consolidation/性能批次P8-P13执行计划-2026-09-16.md §3

### 1.9 决策点(源文档 §10 的原文落点 + 本轮裁定)

**决策点 1 —— P-10 的裁剪上限取值(chain 500 / toolCalls 200)**

  `chain` 500 / `toolCalls` 200;因裁剪是**用户可见行为变更**(界面会出现「已省略 M 条」),
  源文档要求确认后再落地。

    `models/db/schema.rs:41-50` 的 `agent_sessions` 列清单确无 chain(另有 `tool_calls` 表 `:52-61`)。
    故裁剪 chain 是**永久丢失推理链**,与「可从库恢复」的 `toolCalls` 性质完全不同。
  - `toolCalls` 虽可从库恢复,但面板裁剪仍属可见行为变更,收益不抵认知成本。
- **落地**:登记进 [§八 明确不做](05-长期批次与裁定.md#八明确不做知情排除便于复查);P-10 条目状态置「已放弃」。
