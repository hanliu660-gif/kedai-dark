### 二维批次 2 图执行器并行(规模 L,3~10 天)

- **目标**:图节点可并行执行,并保证并发下的状态与取消语义正确。
- **现状证据**:
  - 并行编排先例:`task_engine/team.rs`(JoinSet 并行主 agent)——图并行节点可照抄该并发模型。
  - **已识别的真实缺陷风险**:`set_plan` 是「整列 JSON 覆写」。多个节点并发完成时,
    各自持有 `plan` 的旧快照做读-改-写,会**丢失更新**(节点 A 的 Done 被节点 B 的写入覆盖)。
  - `TaskStep` 现在只有 `name/goal/status/result` 四个字段(`models/types.rs:927-942`),
    而六模式文档把它列为「不动(兼容承诺)」。
- **改动点**:
  1. 图执行器**并行**:JoinSet 调度 + `max_parallel_nodes` 上限;
  2. `TaskStep` 加 `node_id: Option<String>`(serde default)做画布映射——**加性改动**,
     旧客户端反序列化不受影响,**但需同步修订文档中的兼容承诺表述**;
  3. plan 写入串行化:**v1 建议 (a)** 在服务层对 plan 写入做串行化(成本最低,plan 体积小),
     **并补一条并发回归测试**;(b) 新建 `task_nodes` 表做行级更新成本高,为将来留路;
  4. **取消传播到并行分支**;
  5. 并发回归测试。
- **验收断言**:并发 N 节点无丢更新(专测);取消时全部分支收口;usage 汇总正确;
  `cargo test -j 2` 全绿。
- **风险 / 回滚**:风险高(并发丢更新是真实缺陷风险);回滚 = revert(执行器 + plan 写入串行化)。
- **依赖 / 需确认**:依赖批次 1。决策 D5(plan 写入方案)、D8(是否要并行)须确认。
- **状态**:**已完成**(2026-09-19,提交 `927f170`)
  - 落地形态:`AgentFlowConfig.max_parallel_nodes`(**流程级**,缺省 2、范围 1-8、1 = 完全串行,
    越界在保存期 400);执行器改「就绪队列 + 并发上限」调度:上游全部完成(无论成败)即释放
    后继,就绪节点按下标升序取,在飞节点用 `FuturesUnordered` 承载(**未用 JoinSet** 的理由:
    节点 future 借用 `&self` 与流程数据,JoinSet 的 `'static` 约束会把执行器与流程逼成 `Arc`,
    而两者并发语义等价——都是等待 LLM 的异步 I/O);取消检查在**启动之前**,取消后丢弃在飞
    future(分支中止)并统一由「任务已停止」收口,未启动的下游节点保持 pending。
  - **口径修正 1 处(重要,见 [§九 裁定 15](#裁定-15--二维批次-12-的实施口径与原文的三处差异2026-09-19-新增))**:
    原文「改动点 3」建议 **(a) 在服务层对 plan 写入做串行化**——实测**不足以修 IFW-4**:
    只串行化「写」挡不住「A 读→B 读→A 写→B 写」的快照覆盖。改为 **plan 单写者**:并行调度器
    独占 plan(读-改-写全在调度循环内,临界区无 await),节点执行体只回传文本。丢更新的成因
    被结构性消除,服务层无须加锁;该偏差已写入 `遗留.md` §九 IFW-4 迁入说明。
  - 验收:`cargo test -j 8 --no-fail-fast` 1249 passed / 0 failed。并发用例断言
    「轮询观测到 ≥2 行同时 running」(并行确凿发生)+「并发完成后 plan 每行都落库为 done」
    (无丢更新,IFW-4 回归)+「phase=step 各行 token 求和 == 详情 `usage_total`」(记账不变量);
    取消用例断言「下游节点保持 pending、plan 与调用行不再出现未启动节点」。

### 裁定 20 · 二维批次 5a 任务绑定流程 + 流程快照的实施口径(2026-09-22 新增)

- **背景**:本批推进 §四 批次 5 的**改动点 5/6/7**(该批唯一不依赖批次 4 的部分,故拆为 5a,
  拆分依据见该处「拆分」注)。它同时收口了裁定 19 差异 1 记下的那条边界:
  运行态徽标此前读「当前流程库」,故「跑完任务后改流程 / 换当前流程」时徽标可能缺失或与
  当时编排不符。提交:`d3ae0b1`(后端)、`15c659d`(前端)。

- **差异 1 · 原文说「至少落 `flow_id` + 版本」,本批落**闭包全量快照**:
  - **原文说**(`遗留.md` 所属分析稿 §五 批次 5 改动点 6):「在任务创建时把流程定义快照落库
    (或至少落 `flow_id` + 版本),否则用户执行中途改流程会导致任务行为漂移」。
  - **实施结论**:`tasks.flow_snapshot` 存**入口流程 + 其可达子流程闭包**
    (`FlowSnapshot { root_id, flows }`),不取「id + 版本号」。
  - **裁定依据**:运行期的子图解析原本按 id 回读流程库——只冻结根流程的话,
    「改一个被挂载的子流程」仍会悄悄改变已建任务的行为(跨流程生效,最难排查),
    而闭包收集能复用既有的 `sub_flow_edges` 判定(与保存期校验、删除保护同源),

### 裁定 22 · 二维批次 5b(节点级连接 + 节点级工具轮次上限)的实施口径(2026-09-23 新增)

**差异 1:不做节点级 `max_context`（计划改动点 3 的另一半）。**
原文要求「节点级 `max_context`(请求侧通道 `AgentRunRequest.max_context_tokens` 已在)」,但那条通道
**只服务聊天路径**——任务侧目前没有任何上下文裁剪管线(`trim_to_context` 是 `agents::engine` 私有,

**差异 2:节点级模型以「选连接」落地,不引 `PlanStep.model`。**
原文改动点只说「逐节点 provider」。落地时明确:节点引用一条 `ConnectionProfile`

**差异 3:失效引用在运行期**明确报错**,不静默回退默认连接。**
连接被删除/停用后,该节点 error、文案点名连接与成因,其余节点照跑(任务 `partial`)。与 5a
「有 `flow_id` 却无快照 → 明确报错」、6b「子流程不在快照内 → 报错」同口径。代价是「跨机导入的流程
若引用本机没有的连接,跑到该节点会失败」——这是**有意**的:节点级连接的意义就是「这一步由谁跑」,

- **保存期有意不校验**连接引用(流程可导出/跨机导入,而连接是本机设置;保存期拒绝会把可移植流程

- 编辑期由前端选择器**保位显示**「(引用已失效)」并说明运行期后果(与 `TaskFlowSelect` 的

计划改动点 1 明令「不要在 `TaskService` 里另建一份连接器缓存(否则数据源分裂)」。落地时发现

### 裁定 23 · 二维批次 7a(流程搬运)的实施口径(2026-09-23 新增)

**差异 1:导入的判定基准是「内容指纹」而非「id + 内容」。**
原文只说「导出/导入不产生重复 id」。落地时把跳过条件定为**逐字节相同(不含 id)的内容已存在**
(`flow_fingerprint` 把 id 置空后序列化比对)。理由:仅按「同 id + 同内容」判重时,**重复导入
同一份冲突包会每次新增一个副本**(第一次导入因 id 冲突已把那份内容挂到新 id 下,下一次的同一份
内容就不再与本机那份同 id 了)——实测中由集成用例
`flow_bundle_import_remaps_conflicting_id` 的「再导一次应幂等」断言抓出并据此改写。
代价:同内容不同 id 的两份流程无法共存(进库只留一份),这是**有意**的——对用户而言它们就是同一份。

**差异 2:被跳过的流程仍参与引用解析。**
「入口被导入、子流程被跳过」若不处理会留下悬空引用,导入必然 400。故跳过时若本库等价副本的 id
与文件不同,把批内对它的引用**改指向本库那一份**(`remap[old] = kept`)。这条与「批内引用一律
以导入的那份为准」并不矛盾:**只有该流程被跳过**这一种情形才指向本库副本,且两者内容逐字节相同
(区别只在 id)。由单测 `import_rewrites_reference_to_existing_copy_when_sub_flow_is_skipped` 锁定。

**差异 3:导出走 `validate`,不走 `snapshot_for`。**
`snapshot_for` 是**任务绑定**路径,要求流程已启用(绑定一套停用流程没有意义);导出是**搬运**路径,
草稿与辅助子流程(常为停用)同样要能带走。故导出只做结构 + 可达引用链校验,**不看 `enabled`**。
全库导出更进一步:只读不校验(手改脏库仍导得出来)——导入才是写路径,校验在那边把关。

**差异 4:导出文件不含连接定义与密钥,节点级 `connection_id` 原样保留。**
沿用 D7(导出默认不含密钥)与 5b 的失效引用口径:连接是本机设置,跨机导入后编辑期显示
「(引用已失效)」、运行期该节点明确报错。**不做**连接的重映射或剥离——剥离会让「这一步由谁跑」
静默变成默认连接(5b 裁定 22 差异 3 已否掉这条路径)。UI 提示一并写进设置区。

**差异 5(审查轮补):`export` / `import` / `select` 三个 id 在导入侧一律重映射。**
它们同时是 `/api/agent-flows/{…}` 的静态路径段,而 axum 静态段优先于 `/{id}`——id 恰为它们的
流程**删不掉**(DELETE 命中静态路由后按方法不匹配回 405)。本批之前不可能出现这种 id(导入恒分配
UUID),而「沿用文件 id」的新语义让手写 JSON 能造出来;与其让用户撞上「建得出来、删不掉」,
不如在唯一的任意 id 入口处把保留段当成需要重映射。由 `import_remaps_reserved_route_id` 锁定。

**差异 6(审查轮补):导出以**服务端已保存**的版本为准,有未保存修改时先确认。**
改动前 `exportFlowNow()` 直接序列化**草稿**,故「改了没保存就导出」拿到的是编辑中的版本;改走
端点后拿到的是已保存的那份。这是本批唯一一处处**静默**的语义变化,故前端补确认对话框
(取消则不发请求),文件名与提示也改用库中的名字——导出用途是搬到别的机器,给出旧版而不提示
是最坏的一种「看起来成功」。

**同批交付的验收**:后端 1352 例 / 前端 1112 例全绿;`check-contract` 登记三组新映射
(18 → 21 组);变异验证 2 处(引用改写短路 / 保留段短路,逐条变红后复绿)。

### 裁定 24 · 二维批次 7b(对比模式)的实施口径(2026-09-23 新增)

**口径 1:工具形态 —— 单一内置 `run_flow`,不按流程建工具定义(沿用计划原文的偏离标注)。**
`execute_call` 按名查**全局**工具注册表,未注册直接拒绝;而流程名/名册是**用户运行期数据**,
运行期注册会失效 `definitions_cache`(`tools/registry.rs` 的失效点纪律)并让并发任务互相踩缓存。
故工具在启动时注册一次,「哪些流程可调用」由**逐节点改写的 description**表达(随
`params.tools` 下发,不碰全局注册表)。可见性单点:该工具进 `tool_sets::META_TOOLS`,
聊天与 solo/multi/team/plan 一律看不到;只有 `custom.rs` 在对比模式的宽松节点上显式塞进
`tools`(闸门名单由 `tools` 派生,故不需要第二份判定)。

**口径 2:三条闸各自独立计数,报错文案各不相同。**
静态子图深度(`MAX_SUB_FLOW_DEPTH = 3`)与动态嵌套深度(`MAX_FLOW_CALL_DEPTH = 2`)是**两条独立轴**:
动态层不并入 `g.depth`,被调流程内部那套静态子图从 0 层重新起算——否则「同一份流程从入口跑
与从子图深处跑」行为不一致,而用户看不出原因。`MAX_FLOW_CALL_DEPTH` **不复用**
`subagent_max_depth`:那是子智能体设置,复用会让改子智能体深度意外改到流程嵌套。
每任务预算 `MAX_FLOW_CALLS_PER_TASK = 8` 的计数器按任务建在 `run_inner`(随 run 起止,重跑重新计数),
它同时充当 `d<序号>` 的序号来源;超限的调用**消耗序号但不留任何痕迹**(路径永不落地)。

**口径 3:守卫顺序 = 拒绝代价从低到高,且全在任何模型调用之前。**
名单内解析(名单外直接拒,连闭包都不查)→ 环 → 动态深度 → 预算。理由:静态子图的守卫只需防
「手改脏配置」,动态调用的输入来自**模型**,必须假设它会试各种名字——「先解析再判名单」会让
一次失败的调用先烧掉一层 token。被拒的调用不产生任何 `task_llm_calls` 行(测试以此断言「不烧钱」)。

**口径 4:名单原样声明,根流程一律不可被调用。**
运行期可调用集 = `名单 ∩ 冻结闭包 − 根流程`,**描述文案与放行判定同源**(不出现「描述了却调不动」)。
创建期:显式绑定的 `flow_id` 出现在名单里即 400(它正在执行,被调用必然撞环守卫);
未绑定任务(跟随当前流程)无法在创建期判定根是谁,故运行期扣除——扣除后为空则**不注入工具**并 warn,
根流程照常执行(「根流程照常跑」是主语义)。前端不因此暴露空档:勾选区把当前根流程显示为
「(根流程,不可调用)」并禁用。

**口径 5:被调流程内部降级 → 任务 `partial`,但不污染回灌文本。**
与 6b 静态子图同语义:子图内有失败/空产出但成果仍选得出时,本节点成功返回,`NodeOutcome.degraded`
的那条通路换成 `FlowCallState::mark_degraded`(动态层的失败发生在工具调用内部,宿主节点无从得知),
根层收口时并入状态判定。工具返回给模型的**只有纯成果**——降级信号属于任务状态,不属于模型的输入。

**补充 1(运行期宽松口径):未绑定任务的名单成员按「当时的库」解析。**
`current_snapshot(extra_ids)` 对成员取宽松口径(不存在/未启用/结构不合法 → 剔除并 warn):
未绑定任务的快照本就是「执行时才捕获」的语义,成员在创建后被删/停用不该让整个任务跑不起来。
创建期与绑定路径则是**严格**口径(逐项点名 400)——「字段存在但静默无效」的边界只在写入口守住。

**补充 2(成员结构校验必须在名单解析处做):** 名单成员**未必**被任何流程以 `sub_flow_id` 引用,

坏流程会以「描述里列着、一调就报错」的形态漏到运行期。故 `resolve_members` 自己调
`validate_flow`,与保存期同一套规则。

**补充 3(取消与生命周期):调用点用 RAII 注销。**
节点工具循环前 `register_call_site`、守卫 Drop 时注销:节点 future 可能被调度器丢弃(取消),
那种路径不会走到循环之后的代码,漏注销会在进程内留下指向已结束任务的陈旧执行体
(既泄漏内存,也让同一 session_id 在重跑时命中旧条目)。

### 裁定 26 · 二维批次 8(节点级 `max_context`)的实施口径(2026-09-24 新增)

> 计划内**最后一个未启动项**,且原文明确「必须先有裁剪管线设计才可开工」。本裁定的前两条口径
> 即那份设计的结论,其余是落地形态与偏离登记。来源:`遗留.md` IFW-10 边界 1 + 本节批次 8 条目。

**口径 1:裁剪单位取「段级」,不复用聊天侧的 `trim_to_context`。**
任务侧一个节点的输入是**两条消息**(system + user),上游产出全在那条 user 里——聊天侧的消息级
裁剪(从最旧整条丢弃)在这里会**把任务目标连同全部上游产出一起丢掉**,属静默灾难。故本批把
「选哪几段保留」抽成共享原语 `prompt_kit::select_segments_within_budget`(**保留头部段 +
从最旧的上游段起整体省略**,省略按「标签行 + 标记」计成本),计数与渲染留在消费点。
两支裁剪**不是同一件事**,刻意各司其职:聊天侧管「多轮历史」,任务侧管「节点输入装配」。

**口径 2(偏离原文,需明确):缺省取「留空 = 不裁剪」,不是「缺省 = 全局 `max_context_tokens`」。**
计划原文写「全局 `max_context_tokens` 仍是缺省」;实际取**零行为变化**的口径。理由:
批次 8 之前任务侧**从不裁剪**,按字面落地等于让**所有既有流程**的节点输入突然受 64K 全局上限
约束——那是可观测的行为变化(可能截断当前正常工作的长输入),不是「回归」,且与「节点级字段用来
给单个节点**设更小**窗口」的用途正交。**影响面**:想给整个任务侧加溢出保护的用户暂时仍无入口;
该诉求应连同 300s 单次调用看门狗、`tool_history` 预算一起评估,属独立议题(未在本批夹带)。

**口径 3:计数复用引擎同一个 `TokenService`,模型名取节点真实模型。**
新增 `AgentEngine::count_tokens(text, model)`(引擎内部 `Arc<Mutex<TokenService>>` 的唯一对外读点),
不引第二个计数源——否则「同一段文本在裁剪与记账处算出两个数」无从排查。模型名用
`resolve_connector` 给出的**本节点真实模型**(与调用追踪同源,节点级连接的场景下不再是全局模型)。

**口径 4:极端情形明确报错,不静默截断。**
任务目标(恒保留的头部)单独超上限 → 该节点 `Err`,文案点名步骤、带上实际 token 与所设上限;
连「全部上游段都省略」也仍超限 → 同样 `Err`(配置本身无解)。口径同 5b「引用失效不静默回退」、
6b「子流程不在快照内报错」。裁剪**实际发生**时另 `warn` 一次(段数 + 上限),便于事后定位。

**边界:不裁工具轮内历史、挂载节点旁路、严格档同样生效。**
工具轮历史归 `tool_history_keep_rounds` / `tool_history_budget_tokens`(口径不同,本批不动);
挂载子流程的节点把该字段与其它执行参数一视同仁地**旁路**(子图各节点各自裁剪,配置保留);
严格档与宽松档都生效——它管的是输入装配,不是工具面(与 `max_tool_rounds` 的档位相关性相反)。

### 裁定 27 · 自定义流程 A+B 批(闸门可配置化与易用性小尾巴)的实施口径(2026-09-24 新增)

> 非编号批,来源:`展望.md` §八 的 WF-16 / WF-17 / WF-11(UI 成本提示)与 `遗留.md` §三 的四条
> 意识性裁剪(IFW-8 边界 2 / IFW-10 边界 3 / IFW-11 边界 1 / IFW-12 边界 3)。
> A 批与 B 批合为一次交付,但**各自独立可回滚**(A 批只动节点执行参数与设置项,B 批只动任务绑定与搬运)。

**口径 1:节点级超时取「单次调用」粒度,且必须能放宽。**
`PlanStep.call_timeout_secs`(30..=3600)**覆盖**该节点每次 LLM 调用的时间预算:宽松档工具循环**逐轮**
各按它计(与宿主既有 300s 看门狗同粒度)。**为什么不是「节点总预算」**:既有超时语义就是单次调用,
改成整体预算会让「一次很长的工具循环」在两种语义间漂移;**为什么必须是覆盖而非取小**:若实现成
`min(覆盖, 缺省)`,WF-16 触发条件里的「宽/严节点混用同一条时间预算」立刻落空——只能收紧的配置项
等于没有配置项。取值判定抽纯函数 `resolve_call_watchdog`(覆盖优先 → 缺省回落),单测锁两种方向。
超时 = 本节点失败,**不重试**(与口径 2 刻意分离,避免「超时了再重试」把成本重复烧在上游停滞上)。

**口径 2:节点级重试只认「空产出」,并把失败尝试的 token 归并进最终结果。**
`PlanStep.max_retries`(1..=5)= **额外**尝试上限(总尝试 = 1 + n;`Some(0)` 被 400 拒绝——「不重试」
已由「清空字段」表达,不留第二条路径)。**只重试空产出**:连接失效、超时、上游报错一律立即失败。
重试前按 legacy/plan 同一算法翻倍输出预算(`utils::retry::doubled_heal_budget`,封顶 131072)——
空产出最常见的成因是推理吃光预算,只重试不加预算等于重放同一次失败。
**记账是 WF-17 预告的真风险,本批实测命中**:中间尝试各自落一行 `task_llm_calls`,而节点级 usage
只由最终结果携带 → 「各行求和 == `usage_total`」当场破(3 次尝试 109 vs 103)。修法是**归并**:
失败尝试的 token 累加进最终 `NodeOutcome.out`;若最终是硬错误(Err 不带 usage)则**显式补记一行**。
不变量因此仍然成立,而不是被绕过或改断言。

**口径 3:调用闸的两个常量退居缺省值,真源是任务侧设置项。**
`max_flow_call_depth`(默认 2,1..=5)与 `max_flow_calls_per_task`(默认 8,1..=64)落在**任务侧覆盖层**
(`apply!(s, is_task, …)`),消费点(`flow_call.rs` 的三处)改由调用方传入取值,来源是
`TaskRunContext.settings` 快照 →「执行期改设置不影响本轮」的既有语义不变。`MAX_SUB_FLOW_DEPTH`
**不在本批**:它是保存期**结构**校验上限,不是运行期**成本**闸,两者不同轴(与 7b「不复用动态深度」
同一条理由)。设置区间上限刻意保守:两条都是成本闸,调大等于允许更长的模型自主链。

**口径 4:默认节点上下文上限缺省关闭。**
`default_node_max_context`(**默认 0 = 不裁剪**;否则 256..=1048576,与节点级字段同口径)只在节点
未写 `max_context` 时生效。**为什么不像其他缺省那样取一个保守值**:批次 8 之前任务侧从不裁剪,
给整个任务侧默认套上预算等于让**所有既有流程**的节点输入突然受约束——那是可观测的行为变化
(可能截断当前正常工作的长输入),不是「回归」。想要全局溢出保护的用户显式开启。

**口径 5:任务级连接作为「缺省回退」,收口在三处而不是每个调用点。**
`tasks.connection_id` → `TaskRecord` / `CreateTaskBody`;语义 = 该任务所有 LLM 调用的缺省连接
(节点级 `PlanStep.connection_id` 优先),**六模式通用**(绑 provider 不绑编排)。三处收口:
`TaskService::generate_text_timed` 内部回退(覆盖规划/步骤/汇总/team/legacy 的纯生成路径)、
`TaskRunContext.connection_id`(覆盖 custom/solo 的工具循环参数装配)、`AgentLoopCall.connection_id`
(覆盖 plan/team/followup)。自定义节点的**真实模型解析**也改用「生效连接」(节点级 ∪ 任务级)——
否则调用追踪会把走任务级连接的调用记成默认连接的模型。
**创建期即校验引用存在且启用**(400 点名):任务不可跨机搬运(IFW-11 边界 3),不像流程库那样
为可移植性把校验推迟到运行期;运行期引用失效仍按 5b 口径**明确报错、不静默回退**。

**口径 6:改绑 = 重新冻结快照,且只对非进行中任务开放(撤销原「绑定不可改绑」)。**
`POST /api/tasks/{id}/bind` 取**全量替换**语义:`flow_id: null` = 跟随当前流程(解绑)、
`flow_ids: []` = 强制模式,不设「缺键 = 不改」的第三义。原口径的顾虑是「改了绑,旧快照算谁的」;
本批改为**改绑即重冻结** + 拒绝 `planning`/`running`/`planned` 态 ⇒ 该提问不再成立。历史 plan 行
**不动**(徽标按新快照解析,对不上即不显示——IFW-5 既有口径)。新增事件 kind `FlowBound`:改绑既不
是状态迁移也不是计划更新,复用 `Status` 会让「状态没变却收到状态事件」成为常态。

**口径 7:导入覆盖只覆盖「文件里出现过的同 id 流程」,且必须显式请求。**
`on_conflict ∈ {rename(缺省), replace}`(未知值 400——覆盖不可逆,静默回退到 rename 会让用户
以为已覆盖)。`replace` 的三条边界:① 库中其它流程一律不动(绝不「导入即清库」);② 内容相同仍
走跳过(指纹幂等不变);③ 保留段 id 与空 id 仍走重命名(那类没有「本库同一份」可言)。保留 id
⇒ 引用不破,这正是覆盖模式的价值;候选库照常全库校验,失败则整批拒绝、库逐字节不变。

**同批的验收**:后端 `cargo test -j 2` 库内单测 1083 passed / 0 failed、集成文件全绿(唯一红为既有 flake

### 裁定 28 · 文档口径漂移收口批(计数/指称/状态/体例四类)的实施口径(2026-09-26 新增)

> 非编号批,来源:文档漂移专项盘点(三路只读探索 + 逐条实测),无归档源文档;
