### HB-1 成本护栏:token 预算软上限 + 超限刹车

- **目标**:给「模型可自主决定轮数」的路径(chat agent、任务模式主循环、子代理)加一道与 **token 成本**
  直接挂钩的上限,取代当前「只能靠 `max_tool_rounds` 兜底」的局面;超限时不静默,给出可解释的停止原因。
- **现状证据**:
  - 轮次上限:`settings_service/params.rs:144-146` `default_max_tool_rounds() = 32`(可配至 200);
    熔断指纹仅「工具名 + 完整参数」(`agents/engine/executor.rs:716`),窗口/阈值见
    `utils/loop_guard.rs:35-62`。
  - 全仓**无**会话/任务级 token 预算设置项——`rg -n "budget" server-rs/src/services/settings_service/params.rs`
    仅命中 `memory_inject_char_budget`(`:107`)与 `tool_history_budget_tokens`(`:155`),
    两者都是**上下文裁剪**预算,不是成本上限。
  - 实测先例:一次 solo 任务 54 轮 / 300 秒 / 累计 prompt **137 万 token**(`遗留.md` L22「影响面」);
    另一次 7 分钟累计 **150 万 token**(`遗留.md` D4 残余与 `遗留.md` IFW-5 关联;原文误记为 `展望.md`)。
  - 用量已可精确观测:每轮累计 usage(含命中/未命中 token)在 `executor.rs` 聚合,
    收尾经 `run_finish.rs:88-130` 落 `session_usage` / `global_usage`。
- **改动点**:
  1. 新设置字段 `session_token_budget: Option<u32>`(0/None = 关闭,**默认关**)与
     `session_budget_action: warn|stop`(**默认 warn**);补 `params.rs` 默认值与钳制、`secret.rs` 边界、
     设置页对应分区。
  2. 判定点放在**工具循环轮边界**:`agents/engine/executor.rs` 的 `run_tool_loop` 每轮累计 usage 后与预算比较,
     超限按 action 发事件(新 `SseEvent` 或复用 `step` + `agent_status`)并决定是否跳出循环;
     chat 与任务模式共用同一实现(solo/custom/multi 走同一 `run_tool_loop`)。
  3. 停止时**保留已有产出**(正文落库、usage 记账),停止原因写 `extra` 与 info 日志(含已用 token / 轮数)。
  4. 前端:顶栏或 OptimizeModal 显示「本会话已用 token / 预算」;超限提示可关闭。
- **验收断言**:
  - 单测:预算解析与钳制(0 = 关闭、负值拒、上限);判定函数在「等于 / 超过」边界的返回。
  - 集成测试(mock connector 多轮工具循环):小预算 + `stop` → 循环在超限轮后终止、SSE 含预算事件、
    assistant 消息按既有终态落库、`session_usage` 与预期一致;`warn` 档 → 循环继续且**只提示一次**。
  - 前端测试:预算事件渲染 + 设置项序列化往返。
  - 若新增 SSE 事件:四处同步 + `check-contract.mjs` 判别式断言(见上「与 §八 冻结点的关系」)。
- **风险 / 回滚**:风险中——**误杀正常长任务**是主要风险;缓解为默认关闭 + 默认 `warn` 档 + 阈值可调。
  回滚 = 还原设置字段与判定点(无数据迁移)。
- **依赖 / 需确认**:须确认默认档位口径(默认关 vs 默认 warn)与预算口径(累计 prompt+completion vs 仅 prompt)。
  与 HB-2 同域但**独立可交付**,建议 HB-1 先行(预算护栏不依赖熔断算法)。
- **状态**:**已完成**(2026-09-19;提交 `a7e3eb2`)

### HB-2 熔断 v2:同工具 + 输出无实质变化

- **目标**:抓住「同一工具、参数每次略变、输出实质无变化」的空转型长跑,不再只靠 `max_tool_rounds` 兜底。
- **现状证据**:
  - 指纹 = `fnv1a_hash(&[&call.name, &call.arguments])`(`agents/engine/executor.rs:716`),
    窗口 8 轮内同指纹 ≥3 次熔断(`utils/loop_guard.rs:35-62`、默认值 `:52`)→ **参数每次略变即绕开**
    (`遗留.md` L22 判定原文)。
  - 实测形态:连续 54 轮 `bash`,命令各不相同(`ls` → `cat a` → `cat b` …),熔断未触发;
    上下文已收敛但仍烧 137 万 prompt token(`遗留.md` L22)。
  - 既有扩展缝:`LoopGuard::new(window, threshold)` 支持自定义窗口/阈值(`utils/loop_guard.rs:43`),
    **熔断算法本体无需改动**。
- **改动点**:
  1. `utils/loop_guard.rs` 增补一路「语义熔断」判定:在既有指纹之外记录 `(工具名, 输出指纹)` 序列;
     **同一工具名**在窗口内 ≥N 次且其**输出指纹去重后** ≤K 个(实质无变化)时熔断。默认参数保守(N=12、K=2),
     设置页可调。
  2. 输出指纹先做归一化(去时间戳/耗时/绝对路径这类易变噪声),建议口径:「行数 + 前 512 字符 + 去重行集合哈希」。
  3. 熔断行为与现有一致:`agent_status` + `tracing::warn`(含工具名、次数),中断本轮工具循环并按既有终态收尾。
- **验收断言**:
  - 单测:「54 轮不同命令、输出恒定」→ 触发;「同工具不同目标且输出有变化」(连续 `read` 不同文件)→ **不**触发;
    「输出仅时间戳变化」→ 归一化后仍触发。
  - 集成测试:mock connector 经 `[[tool:]]` 钩子重复输出同一内容的多轮调用 → 循环提前终止且 SSE 有提示。
  - 回归:既有 `loop_guard` 单测与工具循环集成用例全绿。
- **风险 / 回滚**:**误杀是主要风险**——`遗留.md` L22 明确「误杀代价高于收益」,故默认参数必须保守,
  且只对「输出无变化」生效(不只看工具名)。回滚 = 关闭新判定(保留 watchdog 日志)。
- **依赖 / 需确认**:**须先裁定触发条件**——`展望.md` L22 的登记口径是「候选解法、待触发」;
  本项以 2026-09-14 的 54 轮实测与 150 万 token 事故为「该形态已再次出现」的证据。
  若维护者裁定触发条件未满足,则本项挂起、只保留 HB-1。
- **状态**:**已完成**(2026-09-19;提交 `12e7d0c`;触发条件裁定为已满足,按默认参数 N=12/K=2 保守实现)

### HB-4 失败与重试可见性:连接器重试入 SSE + 错误卡片消费 `retryable`

- **目标**:用户不再遇到「界面停几十秒然后报错」的无解释等待,也不再有「可重试却没有重试入口」;
  **不改任何自动重连/退避算法**(§八 冻结点)。
- **现状证据**:
  - 连接器重试(最多 3 次、500ms×2^n 退避、尊重 `Retry-After`)**只写 tracing、不注入 SSE**
    (`connectors/openai_compatible/retry.rs:43-44` `tracing::info!("模型请求重试")`)→ 等待期前端无信号。
  - `retryable` 字段已在线格式里(`web/src/api/types.ts:124`),但 `sseReducer` 的 `error` 分支
    只把 code/message 写进链(`web/src/sseReducer.ts:198-215`),**不消费该字段**,界面无重试按钮。
  - 聊天流失败时前端本地合成 `step` + 空 `finish` 复位(`web/src/api/chat.ts:109-128`)——复位正确
    (避免永久卡「生成中」),但用户侧表现为「回复凭空消失」。
- **改动点**:
  1. 连接器在**即将重试前**经现有 sink 发轻量事件(建议新 `SseEvent::Retry { attempt, max, reason }`;
     若不愿扩线格式可复用 `step` + `agent_status`),前端显示「正在重试(1/3)…」,成功后清除提示。
  2. `sseReducer` 的 `error` 分支消费 `retryable`:不可重试(401/403/参数类)只提示;可重试(429/5xx/超时)
     在错误卡片上给「重试」按钮,**复用既有重新生成端点**而非新造接口。
  3. 补重试/退避的时序测试:`retry_delay` 的退避序列与 `Retry-After` 上限
     (`connectors/openai_compatible/retry.rs:11-23`)当前**无测试**。
- **验收断言**:
  - 集成测试:mock connector 注入 429(`[[fail:]]` 钩子)后成功 → SSE 序列含重试事件且最终 `finish`;
    不可重试错误(400/401)不产生重试事件。
  - 单测:退避序列(500 / 1000 / 2000,封顶 5s)与 `Retry-After: 60` 被钳到 30s。
  - 前端测试:error 分支 `retryable=true` 渲染重试按钮、`false` 不渲染;点击走既有重生成路径。
  - 新增 SSE 事件按四处同步纪律 + `check-contract.mjs` 判别式断言。
- **风险 / 回滚**:风险低-中(新增事件需四处同步,漏一处会被门禁拦下);回滚 = 移除事件与按钮,
  连接器行为不受影响。

#### 一、目标与验收断言

- **目标**：聊天侧一次被中断的运行（点停止 / 连接错误）可从既有会话状态**继续**，
  且模型上下文里带着「上一轮已完成哪些工具调用」的清单，不再从零重做。
- **验收断言（实施批次逐条落成测试）**：
  1. 中断后 `agent_sessions.state` 为 `interrupted`，`GET /api/chat/sessions/{id}/agent/trace`
     可见；续跑起跑后该行**不重建**（同 id），其 `tool_calls` 行只增不减；
  2. 续跑 run 的模型输入里含「已完成工具调用」清单块（逐条：工具名 + 锚点参数 + 结果摘要）；
  3. 普通新消息路径逐字节不变（会话行照旧清旧建新；既有测试全绿）；
  4. 续跑中途再 stop → 再次 `interrupted`，可再次续跑（链式）；
  5. 清单上限（条数 / 字符）超出时显式省略并注记省略条数（不许假装全量）；
  6. `state=finished` 或无 trace 记录时调续跑端点 → 400 明确文案（不静默建新运行）；
  7. 前端：可续跑态显示「继续」入口，点击走续跑端点并接同款 SSE；finished / 无记录不显示；
     既有 trace 面板行为不变。

#### 三、设计决定（均附推荐档；拍板后实施）

- **D1 可续跑判定与入口落点**
  - 判定**单一出处**在后端：`agent_sessions.state ∈ {interrupted, error}`。trace 端点已在
    返回该 state（前端 Agent 面板已消费）——判定零新数据流。
  - 落点：(a) **Agent 面板 / 状态条**（判据现成）【推荐】；(b) 中断消息旁（需消息级标记，
    error 场景无对应物）；(c) 两处都放。(a) 之外若实测可发现性差，再迭代加 (b)。
- **D2 生命周期切换口径**
  - (a) **仅续跑入口保留**会话行与 `tool_calls`；普通新消息照旧「清旧建新」
    【推荐——默认路径逐字节不变，改动只作用于新入口】；(b) run 开头一律不再删除。
  - 续跑实现：引擎新增 `resume` 分支——`find_by_session` 命中且 state 合法 → **复用**该行
    （不 delete / 不 create）；工具调用继续挂在同一 `agent_session_id` 下，链式续跑自然成立。
- **D3 读回语义（「不重复已完成工具调用」的上下文面）**
  - (a) **清单作为续跑输入文本、不落库**【推荐】：续跑前读 `list_tool_calls(agent_id)`
    （该行下全部已完成调用 = 上一轮中断前 + 此前续跑段的累积）生成清单，拼进本轮的
    `user_input`——走引擎既有用户消息通道，**复用全部消息构建 / 压缩 / 裁剪路径，零新注入缝**；
    续跑路由**不落库**这条输入（历史只会多出本轮 assistant 成品，与普通轮一致）。
  - 清单格式逐条：`N. <工具名> <锚点参数> → <结果摘要>`；**锚点取值复用 HARNESS3-3 机制**
    （`tool_sets::state_anchor_arg` + `agent_tools_fs_patch::patch_anchor` 的值制分派，
    trim.rs 同款——单一出处，不为续跑写第二套）；结果摘要取首行 + 原长度。
  - 上限（常量，超限显式注记）：条数 ≤30、总字符 ≤4000；清单块尾部附一句
    「以上均已执行完成，请继续完成目标、不要重复这些调用」指令。
- **D4 防重复执行的强度**
  - (a) **软约束**——清单进上下文 + 指令明示【推荐 v1】；模型行为是概率性的，机器断言
    只覆盖「清单在场」与「状态没丢」，**不宣称「保证不重放」**；
  - (b) 软约束 + **只读调用精确去重**（命中回放旧结果）——记为待办（旧结果可能过期，
    需先解决新鲜度判定）；(c) 全工具去重——不可行（副作用工具的重放有真实语义，如重跑构建）。
- **D5 任务侧（「聊天与任务分别决定」的落地）**
  - (a) **不做**【推荐】——任务侧状态本就逐步骤落库（`plan` / `result` / 任务消息），重跑 =
    「带全量历史重新规划」；plan 模式已有 approve 续跑形态。E46 的纪律落点即「分别决定」：
    **本设计范围 = 聊天侧**，任务侧维持现语义、不新增续跑（如实登记，非遗漏）。
  - (b) 任务侧断点续跑（需动任务引擎的取消 / 步骤恢复，规模另估）。
- **D6 接口形态**
  - 新端点 `POST /api/chat/sessions/{id}/agent/resume`（空体）【推荐】——send 的用户消息
    落库与前置校验语义对续跑不适用；实现复用 send 的 SSE 事件面与 `pending_runs` 中止机制
    （续跑期间「停止」照常可用）。路由侧先校验可续跑态（不合法 400）；引擎内部再验证一次
    （防竞态，失败走既有 error 事件）。
  - 复用 send 加 `resume` 标志（备选；与用户消息语义耦合，不推荐）。

#### 四、实施切片与量级（拍板后另开批次）

1. **引擎**：`AgentRunRequest` 加 `resume`（加性默认 false）+ resume 分支（复用会话行）+
   清单构造器 + 单测（保留 / 清单内容与上限 / 链式 / 状态校验）；
2. **端点**：`/agent/resume` + 集成测试（中断→续跑→完成；finished 400；再中断链式；
   续跑期间 stop 可用）；
3. **前端**：Agent 面板「继续」入口 + 组件测试；
4. **留档**：六处同步 + 计数回填。**概估 1d 量级**（不含任务侧）。

#### 五、边界（不做，防顺手加）

不做自动续跑（必须显式点「继续」）；不做硬去重（D4-b 待办）；不改消息持久化与既有 SSE
语义；不新增表 / 列（检测信号 state 与 `extra.interrupted` 均已存在）；任务侧不动；
不为续跑复制锚点 / 摘要的第二套实现（单出处复用）。
