## <a id="2026-09-27-toolchain"></a>2026-09-27 Rust 工具链口径落地 `rust-toolchain.toml`（QUALITY-FIX Q3）

> 来源：`docs/plans/QUALITY-FIX-PLAN.md` 批次 3（Q3）。**执行前纠正了该稿的一条前提**：
> 它建议 CI 侧改 `dtolnay/rust-toolchain@master` + `with: toolchain-file:`，而该 action **没有这个输入**
> （维护者在 issue #77/#116 两次明确拒绝支持 `rust-toolchain.toml`）——方案在地板上不成立，
> 已在执行时就地改写（见下「为何这么改」与 `经验.md` E63）。

**改了什么（条目化）**

- 新增仓库根 **`rust-toolchain.toml`**：`channel = "1.97.1"`，`components = ["rustfmt", "clippy"]`；
  文件头写明生效范围、升版五步、以及「刻意不声明 Android 交叉目标」的理由（声明后 CI 每次 run
  都要为 4 个 rust-std 额外下载，而 `~/.rustup` 不在 CI 缓存面内）。
- `.github/workflows/ci.yml`：Setup Rust 步的注释重写——**真值源是本文件**，`@1.97.1` 是必须手写
  同步的第二处；步名改为「锁 1.97.1,真值源 rust-toolchain.toml」。
- `tools/check-doc-claims.mjs` 新增第 11 条口径 `toolchain-version`：派生器读 toml 的 `channel`，
  两条 extra 断言 `ci.yml` 的 `@<版本>` 与 `MAINTENANCE.md` 的工具链行同值。版本是字符串，走
  extra 的直比路径（`checks` 的 `gotNorm` 分支只支持数字与字母区间）。
- `MAINTENANCE.md`：工具链口径行（原文写「CI 用 `@stable`」，与 `ci.yml` 实况早已不符）+ 工具链
  表行 + doc-claims 派生项清单；`docs/契约.md` §5（10 项 → 11 项）与机检状态总表；
  `docs/契约-协议与配置.md` 门禁清单；`docs/经验.md` 新增 E63 + E60 补记。

**为何这么改**

E60 的根因是「版本号只存在于 CI yaml + 人的记忆两处」——文档记教训只是缓解。原方案的
「让 CI 读同一个文件」在 dtolnay 的 action 上做不到，故改为**制度化的等效解**：toml 做本地唯一
真值源（rustup 代理在仓库内任何 cargo/rustc/rustfmt/clippy 调用都会解析到它，换机、换会话、
`rustup update stable` 都不再改变口径），CI 与文档两处由门禁逐条钉死。**单一出处追求的是
「只有一个地方需要手写」，而不是「只有一个地方存在这个字符串」。**

**验证证据**

- 前置：`rustup toolchain install 1.97.1 --component rustfmt,clippy`（本机原先只有 `stable`——
  其版本恰好也是 1.97.1——与 `1.98.0`；按版本名 pin 需要**真名为 1.97.1** 的工具链）；
  4 个 Android 交叉目标同步补装到该工具链。
- `rustup show active-toolchain` → `1.97.1-x86_64-pc-windows-msvc (overridden by 'D:\\kedai\\rust-toolchain.toml')`；
  `cargo --version` → `1.97.1 (c980f4866 2026-06-30)`。
- **切换工具链没有触发全量重编译**：`cargo build --workspace` 只重编 `kedai-server`，33.2s
  （rustc 版本串与 `stable` 相同 → 指纹命中，依赖产物全部复用）。
- **反向验证门禁真的生效**：把 toml 的 channel 临时改成 `1.98.0` → `node tools/check-doc-claims.mjs`
  **exit 1** 并同时点名 `ci.yml` 与 `MAINTENANCE.md` 两处不一致；改回后 `[ OK ] 11 项`。
- `tools/check-all.ps1 -Quick` **全部通过（exit 0）**：cargo fmt 1.5s / clippy 58.5s /
  cargo test --workspace 266.1s / 其余 10 段 gate 无红。

## <a id="2026-09-27-split"></a>2026-09-27 巨型文件拆分 · Q1 五刀（QUALITY-FIX Q1）

> 来源：`docs/plans/QUALITY-FIX-PLAN.md` 批次 1（Q1）。五刀各自独立提交：

> **执行前纠正了该稿的一条前提**：它写「共享辅助函数收敛到 `tests/macros.rs` 已有的公共层」——
> 实测 `tests/macros.rs` 是 macros 接口的**测试二进制**、不是公共层，全仓根本没有共享层
> （40 个测试文件里 36 个各自复制了 `test_app`）。故按仓库既有体例「谁用谁带」，不新建
> `tests/common`（理由见下）。

**改了什么（条目化）**

| 刀 | 旧 | 新 | 提交 |
|---|---|---|---|
| 1 | `tests/tasks.rs`（3944 行 / 65 用例） | `tasks_crud`（19）、`tasks_prompt`（4）、`tasks_modes_solo_multi`（9）、`tasks_modes_plan`（19）、`tasks_modes_team`（10）、`tasks_followup`（4） | `b159c42` |

| 3 | `services/agent_flow_service.rs`（3249 行，全仓最大生产文件） | 目录模块：`mod.rs`（公共词汇 + re-export，288 行）/ `service.rs` / `graph.rs` / `subflow.rs` / `library.rs` / `bundle.rs` / `tests.rs`（原内联测试 1716 行） | `a20bc13` |

| 5 | `services/memory_service.rs`（1662 行） | 目录模块：`mod.rs` / `service.rs` / `recall.rs` / `distill.rs` / `vectors.rs` / `tests.rs` | `e1d4634` |

**为何这么改**

- **测试文件拆分的实质收益是隔离**：`tests/` 下每个 `.rs` 是一个**独立测试进程**，
  `build_test_app()` 的 `DATA_DIR`（`%TEMP%\kedai-test-<pid>`，按 `process::id()` 命名）与
  `OnceLock` 单例 app 随文件独立。原先「同一进程内共享 settings.json / 设置覆盖层 / 流程库」
  的顺序耦合（`遗留.md` TEST-ISO-1 的同一土壤；两个大文件自己的注释也承认过这一约束）**随之消失**。
  这同时把「多会话并行改测试」的最大冲突面切小了。
- **刻意不建 `tests/common` 共享层**：`count-tests.mjs` 递归统计 `tests/**/*.rs`，共享文件会让
  「集成文件数」口径虚高并需长期维护；更要紧的是它会给多会话并行制造**新的争用点**，与拆分用意相悖。
- **生产文件的目录模块化保持对外 API 零改动**：类型与常量留在 `mod.rs`，子模块的自由函数由
  `mod.rs` 逐个 `pub use`，故 14 处外部 `use crate::services::agent_flow_service::…` 全部原样可用；
  跨子模块共用的私有辅助只放宽到 `pub(super)`（**未新增任何 `pub`**）。
- **CSS 按「连续区段」切是关键**：拼接顺序 == 原顺序 ⇒ 级联等价；不引入 `@layer` 包装
  （手写 CSS 全部 unlayered，套 `@layer` 会被 Tailwind 工具类反超）。

**验证证据**

- **纯移动**：四刀都用脚本解析顶层项后逐项搬运，校验「原文件 == head + 全部项」且项间无游离文本
  （residue 均为 0）、每项文本在产出里出现次数正确、且是所属文件里的**逐字连续子串**。
- **测试块体内容零改动**（生产刀）：把原 `mod tests` 块体与新 `tests.rs` 去掉全部空白后比对——
  `agent_flow_service` 两侧均为 43616 字符**完全相同**（2 处续行由 rustfmt 因缩进变浅而合并）；
  `memory_service` 再去掉逗号后均为 15118 字符**完全相同**（唯一的非空白差异是 rustfmt 去掉的
  1 个尾随逗号）。两处均为排版级别的等价。
- **CSS 产物逐字节相同（受控 A/B）**：用 git 把源切回拆前状态分别构建，只留「是否拆分」一个变量
  —— 两侧 `index-*.css` 均为 **sha256 `2a959af9…` / 88225 字节**，首屏 275247、全部资产 478583、
  chunk 55 完全一致；`!important` 处数拆前拆后均为 13。
- **计数口径**：`backendIntegration` 338、`backendTotal` 1462 全程不变（用例数不变），
  `backendIntegrationFiles` 40 → 51；`MAINTENANCE.md` 两处复写同笔更新。
- **全量**：每刀后 `cargo fmt --check` + `cargo clippy --all-targets -- -D warnings`（零告警）+
  `cargo test --workspace -j 8`（**显式捕获退出码**，CARGO_EXIT=0；55 个二进制 1450 passed / 0 failed，
  与拆分前逐字相同）；`check-contract` / `check-arch` / `count-tests --check` / `check-doc-claims` 全绿；
  `npm test -w web` 1213 passed / 113 文件不变。
- **云端实证（2026-09-27，run `36292647002`，全套 8 笔推送后触发）**：CI **completed / success**
  （52m47s），15 段全 `[ OK ]`（cargo fmt 2.7s / clippy 145.1s / **cargo test --workspace 1471.4s** /
  audit 两锁+npm / 契约 / 架构 / count / doc-claims 11 项 / ratchet / eslint / vue-tsc / vitest /
  vite build / bundle budget）。
  **关键一条**：此前在 CI 上 **2/2 稳定复现**的
  `state_block_auto_injected_into_system`（当时报在 `tests/api_integration.rs:1170`，本地默认并行下
  却通过，被定性为「测试隔离缺陷——某条前序用例污染共享状态」，修复归「另一批次」）本次
  **`test state_block_auto_injected_into_system ... ok`** ——**那一批次就是本批**：用例搬进独立测试
  文件后各占一个进程与独立 `DATA_DIR`，跨文件污染源不再可达，隔离缺陷由构造消除而非加锁掩盖
  （机理见 `经验.md` E65）。

**门禁三处同笔修改（不改就红，均已实测复现过）**

1. `tools/check-contract.mjs` 硬编码两条服务的源文件路径，且其 `read()` **无 try/catch**——路径不改
   会让整条 `npm run check` 以 ENOENT 裸崩（非友好 FAIL）。8 条映射同笔改指 `…/mod.rs`。
2. `tools/check-arch.mjs` 的 `productionLineCount`/`productionSource` 原本只认列首 `#[cfg(test)]`：
   测试搬到独立文件后那个文件会被**整体当成生产代码**，规则 E（`services` 生产代码禁用 `.expect(`，
   基线是空集）会把测试里的断言全部判红。两条正则放宽为 `^#!?\[cfg\(test\)\]`，新 `tests.rs` 列首写
   `#![cfg(test)]`；放宽是**严格超集**（全仓列首 `#![cfg(test)]` 命中数为 0），故对其余 100+ 个文件无副作用。
3. `tools/arch-layers.json` 增登前端目录 `styles`（L1）：规则 I 要求 `web/src/` 下**每个目录**都登记
   代际，不登记直接 FAIL（实测复现）。

**为何这么改**

- **偏好走独立键而不是改粘性键**：用户原文要求「偏好决定每次启动的默认模式」，而现状是「上次用过的模式」；
  新增 `kedai.default-app-mode.v1` 后，**未设偏好的老用户行为逐字不变**（仍读 `kedai.appMode`），
  偏好只在走过引导或显式设过设置项的机器上生效——升级零影响。
- **浮条不渲染遮罩**是「带我去设置」能成立的前提：遮罩全屏会挡住刚打开的综合设置。
  教程展开态 z-index 高于模态（`--z-tour:80`），回到展开态盖住设置；结束/跳过只关「由教程打开」的设置
  （`openedSettingsByTour`），不碰用户自己开的那个。
- **步骤表是纯函数、文案表在懒加载组件里**：首屏 index chunk 只多一个几百字节的 L1 模块，教程文案随弹窗 chunk。
- **`SettingsSectionKey` 上移 L1**：该键被 stores(L2) 与 components(L3) 共用，留在 SettingsHub 会让 L2 反向依赖 L3。
- **教程期间冻结计划**：第二问作答时即定下步骤序列，中途切模式不重算（防步骤跳变）。

## <a id="2026-09-28-coding-bundle"></a>2026-09-28 编码能力包：任务模式编码执行者缺省词（HARNESS3-6 落地 · 设置项默认关）

**背景与裁定**：用户拍板「编程能力补全以官方能力包形态交付、**默认关、显式启用**」。这条同时是对
`计划.md` 长期悬置的「编码能力是否入产品面」定位问题的回答——**以可选能力包入产品面**，默认形态与
`README.md` / `功能.md` 的能力面叙述均不变；`PRODCAP-4` 不降级（按原批推进）；HARNESS3-6 的
「先拍定位再动手」约束随之解除。本批是该能力的第一个可交付切片：把编码场景的执行姿态收进一个可显式
启用的模块边界（**不是**新增工具——工具面在 D1 批已上线：`fs_*` 族 + `bash` + 工作区闸门）。

**调研结论（决定了本批的形态）**：评估「做成插件」时核对了既有机制——`ToolRegistrar` / `ToolOrigin` /
`register_external` / `data/plugins/tools` 这套工具插件机制**只覆盖「工具」这一层**，而 HARNESS 提交 3
七项里另五项（取消中止 / 续跑 / 压缩保留 / 自测闭环 / headless 入口）是内核行为或独立二进制，插件机制
插不进去；且现有插件脚本刻意收窄（无 eval、白名单指令求值），装不下编码逻辑。故本批**不新建插件机制**，
改用仓库既有的「单一出处常量 + 设置开关」体例承载；两处对既有实现的安全修正：**不加** `ToolOrigin`
档位（实现是内核 Rust、参数走同一套 `workspace_guard`，语义本就是 `Builtin`；新增档等于放宽授权裁决）、
**不建** `data/` 下的声明目录（身份若来自可写目录即有伪造面）。

## <a id="2026-09-30-coding-bundle-b2"></a>2026-09-30 编码能力包续做批次 2：自测闭环（命令上限 1800s + 输出保头保尾 · HARNESS3-4 落地）

**背景与裁定**：承接同日的[批次 1](#2026-09-30-coding-bundle-b1)。§十六 的编码执行者模板要求

（本机实测 1~16 分钟）之下——**自测跑不完，纪律就落空**；且失败摘要位于输出**尾部**，
旧截断只保头，即便跑完也看不见为什么失败。落点即 `计划.md` HARNESS 提交 3 的第 4 项。

**改了什么**

| 项 | 改动 | 落点 |
|---|---|---|
| 命令上限 | `MAX_TIMEOUT_MS` 300_000 → **1_800_000**（缺省 `DEFAULT_TIMEOUT_MS=60_000` **不动**，常态体感不变） | `services/exec/mod.rs` |
| 跟随①：注册表 | `bash` 的整工具超时由硬编码 `330s` 改为 **`MAX_TIMEOUT_MS` + 30s 收尾余量派生**。不跟的话注册表先掐断并把 future drop 掉，exec 层的强杀与审计文案全部失效（长命令表现为「工具超时」而非「命令超时」） | `tools/bash.rs` |

| 跟随④：步骤预算 | 默认 1200 → **3600** | `settings_service/params.rs` |

| 引擎常量露出 | `TASK_TOOL_LOOP_CALL_TIMEOUT` 由 `const` 改 `pub(crate)`，供看守下限引用（不留第二份手写的 300） | `agents/engine/executor.rs` |

**为什么这么改（三处台账未记的耦合，是本批的真正内容）**

1. **空闲看守**：`idle.rs` 模块头自陈「工具循环期间不落库、不发事件」，心跳只由
   `register_cancel` 与 `emit_event/emit_llm_call` 刷新。所以一条跑满 1800s 的命令期间任务
   **完全静默**，按旧默认 900s 会被看守以 `finish_ended` 收尾——现象伪装成「任务空闲超时结束」，
   比报错更难归因。抬上限必须同批校准下限与默认值。
2. **步骤墙钟预算在轮末判定**（`executor.rs::step_budget_reached`）：预算小于命令上限时
   **不会截断命令**，只会砍掉后续轮次——即「跑完一次长自测就带产出收尾」，失败之后没有下一轮去修，
   自测闭环退化成一轮抽签。这一处隐蔽到台账完全没提。
3. **截断是两层**：内层按**字符**、外层按**字节**；CJK 下内层 32768 字符可达 ~98KB > 外层 64KB，
   只改内层的话，辛苦保住的尾部会在外层被二次切掉。故两层同批改，并留一条用例
   （`truncate_budget_under_multibyte_worst_case`）钉住「内层最坏字节量确实超外层预算」这个前提。

  `full_length_command_silence_is_not_idle`（静默 = 命令上限时按下限**不算空闲**）、

  `is_idle` 在该静默下为假），属把耦合变成机器可见的**替代证据**，不是端到端证据；

  命令本身 + 收尾余量，模型调用不在这条 future 里。已改为正确的关系断言。
- 全量 `cargo test -j 8`：**1464 passed / 0 failed**（55 个测试二进制；静态 1476，差值为平台门控用例）。

**边界与遗留**

**为什么与台账原案不同(这条是本批的真正内容)**

  **150 万 token**、单次调用 88 万,当时的修复就是把参数回收为占位。整轮豁免等于
  把 R3b 已经关掉的口子重新打开,长任务会直接顶穿预算。
- 改为「**照旧占位化,但把锚点留在占位里**」:验收(跨压缩记得改过哪些文件)达成,
  回收能力不损失,且两侧都能被断言锁住。

**为何这么改**
