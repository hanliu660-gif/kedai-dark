## <a id="2026-09-30-code-bundle-a4"></a>2026-09-30 编码能力包功能扩展批次 4：内置流程库并入编码流程预设（CODE-5 落地）

**背景**：`计划.md`「编码能力包功能扩展（CODE-1~CODE-5）」章 CODE-5 条目；用户拍板
**Q5=(a)** 2 条流程、**D3=(a)** 写盘 seeding、**D4=(a)** 实现流程放开写工具与 bash。
**本批自建并入缝**：原计划写的「照 LIT-5 同缝」在详细设计阶段被核实为**无据可依**——
LIT-5 与其依赖 LIT-1 均未启动，`AgentFlowLibrary` 当时只有 `current_flow_id` + `flows` 两个字段，
seeding 只有「库文件缺失」「旧单流程格式」两个触发点，构造点也读不到 settings。设计稿已把
该修正与工时上调（1d → 1.5~2d）写进条目；本批按修正后的口径施工。落地提交：`03634c9`
（后端：并入缝 + 两条常量 + 两个触发点 + 两个集成文件），文档收口见本条目。

**改了什么**

1. **并入缝（单一出处）**：`AgentFlowLibrary` 加加性字段 `seeded_pack_ids`
   （`skip_serializing_if = "Vec::is_empty"` → 未开过包的库文件**逐字节不变**，有一条测试直接
   断言文件里不出现该键）。它同时承担「防重复注入」与「删过/改过不复活」——注入过即记账，
   故**不需要墓碑字段**。`library.rs` 新增 `pack_flows(开关)`（「开关 → 流程常量」的唯一映射点）
   与 `merge_pack_flows(lib, packs)`（唯一的合库函数：只 push、**不动 `current_flow_id`**、
   返回是否有变更）；`service.rs` 新增 `sync_pack_flows(开关)`（有变更才落盘）。
2. **两个触发点**：① `app_state.rs` 构造期按开关并入一次（覆盖「库文件已存在但从未注入」的
   升级路径）；② `api/settings.rs::update_settings` **成功落盘后**的写入钩子按开关同步一次
   （运行期翻转**无需重启**）。两处都读**有效值** `for_mode(AppMode::Task).task_coding_bundle_enabled`
   （与任务侧读法同源）；钩子失败只记 error、不让设置保存失败。
3. **两条常量流程**（`coding_pack_flows`）：`builtin-code-review`「代码审查流程」
   （只读侦察 → 逐项审查 → 核验 → 报告；**全程只下发只读三件套**）、`builtin-code-impl`
   「实现·自测·复盘流程」（阅读与计划 → 最小实现 → 跑验证并修复 → 复盘 → 交付摘要；放开
   `fs_write`/`fs_edit`/`bash`）。工具白名单从 `tool_sets::WORKSPACE_TOOLS` /
   `WORKSPACE_READONLY_TOOLS` / `bash::TOOL_NAME` 三个**既有单一出处**常量派生，不手抄名字。
4. **前端两处改动（其中一处是复核时补的缺陷修复）**：三处消费点与两个选择器都读「库里的全部流程」，
   服务端一注入即**接口可见**；前端只需 ① 补一处 TS 类型（`AgentFlowLibrary.seeded_pack_ids?`，
   契约门禁要求线上字段必须声明）；② **开包保存成功后刷新流程库**——`CodingBundleSection.onToggle`
   成功后调 `store.loadAgentFlow()`。② 是**收尾复核时发现的实测缺陷**：流程库缓存在
   `stores/genSettings.ts` 的 ref 里，而各消费点（`TaskFlowSelect.vue:108` / `TaskBoard` /
   执行流程区）都写成「**未加载才拉**」，故开包后「绑定流程」下拉与流程列表要**重开设置或重启**
   才看得到新并入的流程——建任务时选不到刚开出来的编码流程，等于「一键选用」不成立。
   两条前端用例锁死该行为（成功后刷新一次 / 保存失败**不**刷新，因为未落盘就没有新流程可看）。

**为何这么改**

- **写盘 seeding 而非读时合并**（D3=(a)）：三处消费点（`api/chat.rs`、`api/agent.rs`、
  `task_service`）都读 `self.library`，写盘后**服务端消费面零改动**（前端需要上面那一次刷新，
  见第 4 条）；读时合并要改 `get`/`flow_by_id`/`get_library`/`set`/`remove`/`export_bundle`/
  `flow_index` 等约 10 处 `self.library` 直接用点 + 新增墓碑字段，回归面覆盖 custom 全路径。
  代价是**关包不回收已注入副本**（既定边界，同 LIT-5 Q2）。
- **不给不可能的场景加防御**：实测 `bash`/`fs_*` 恒在注册表（`registry.rs` 不按授权档位裁剪，
  档位只影响**执行期**裁决），故 `validate_flow` 的「tools ⊆ registered_tools」恒过，
  **不需要**注入时按注册表过滤白名单。
- **两条流程的工具面刻意分工**：审查流程只读 → 「审查不会改文件」是**结构保证**而非提示词请求；
  实现流程才放开写与命令，并把「命令被拒/工具不可用/失败都要如实报告，不得假装通过」写进
  自测步骤正文（默认档 `deny_dangerous` 对 `bash` 按名例外，但命令级硬门仍拒破坏性命令；
  用户切成 `allowlist` 档时 bash 根本不下发——两种情形都会落到「如实报告」这条纪律上）。

## <a id="2026-10-02-vision-fix"></a>2026-10-02 视觉能力包修复批次（工具图像落位 / 纪律注入 / 解码上限 / 截图钳制）
