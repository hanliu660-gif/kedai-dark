### 一、P-8 首屏拆 `modal-settings` 反向耦合（提交 `c532a11`）

**改了什么**：`web/vite.config.ts` 删除应用代码段**全部** `manualChunks` 归组
（`modal-settings`/`modal-prompt`/`modal-contracts`/`modal-devtools`/`modal-worldbooks`），
应用代码改由 Rollup 默认分块；`node_modules` 的三组（vendor/vue-vendor/content-rendering）不动。

**为何这么改**：`SettingsModal`/`SettingsHub` 静态 `import` 了 `store.ts`（顶层实例化全部子 store）、
`api`、composable，这些模块**同时被首屏入口引用**。强制归组把它们一并拖进 `modal-settings`，
于是 `index.js` 出现对该 chunk 的静态边 → `index.html` 发出 `modulepreload` →
首屏白拉 188,635 B / gz 62,793 B，动态 `import()` 的懒加载语义形同失效。

**与计划文档拟定方案的一处偏差（已按实测调整）**：计划只要求删 `SettingsHub`/`SettingsModal` 两条规则，
实测**不足**——耦合会原样搬到 `modal-worldbooks`（25.9 KB → 191 KB，比原 chunk 更大），
因为每个归组组件都静态 `import ../store`。故归组必须**整体**去掉。

**验证证据**

| 项 | 改前 | 改后 |
|---|---|---|
| `index.html` modulepreload 含 `modal-*` | 是 | **否**（只剩 vue-vendor/vendor/content-rendering + 2 CSS）|
| `index-*.js` 静态边 | 含 modal-settings | 只剩三个 vendor chunk |
| 首屏合计 raw | 774,952 | **745,413**（−29,539）|
| 首屏合计 gzip | 271,621 | **260,793**（−10,828）|
| chunk 数 | 32 | 34 |

- `npm test -w web` → 89 文件 / 876 用例全绿（`modals.test.ts` 零 chunk 归属断言，不受影响——
  计划文档担心的「可能断言 chunk 归属」经核实为虚惊）。
- `npm run typecheck -w web`、`check-frontend-lint.mjs`、`check-arch.mjs` 均通过。
- **计划文档预期「首屏少 188,565 B / 61,850 gz」不成立**：该 chunk 中大部分是被入口共享的模块，
  去掉归组后它们仍需进首屏（只是改为并入 index chunk），真正可移除的只有弹窗实现本身。实测收益即上表。

### 二、P-9 渲染缓存有界化 + 虚拟滚动条数窗口（提交 `09a9e04`）

**改了什么**：新增 `web/src/renderCache.ts`（有界缓存容器 `createBoundedCache`，容量 500、FIFO 淘汰、
含 hits/misses 统计）与两个模块级实例 `messageHtmlCache`/`scriptBlocksCache`；
`ChatMessageItem.vue` 的 `html` computed 改为「先查模块级缓存，未命中才渲染」，渲染分支抽出为
`renderMessageHtml()`；`ChatWindow.vue` 的 `scriptBlocksCache` 由「组件作用域裸 Map（无上限）」改为模块级有界；
`useVirtualMessages.ts` 新增条数窗口 `rowWindow`（默认上下各 8 条），与像素窗口取较大者。

**为何这么改**：虚拟滚动在消息离开缓冲区时会**卸载组件**、降级为等高占位 div；滚回来重新挂载时，
`html` 是**组件内 computed**，缓存随实例销毁 —— 同一条消息来回滚动反复重付
`renderScopedScripts`/`renderMarkdown`/`sanitize-html`（实测 sanitize-html 处理 16.8k 字符 ≈ 3.057ms，
约 markdown-it 的 7 倍）。提到模块级即可跨实例存活。顺带收敛两处既有缺陷：`ChatWindow` 原缓存
「无上限 + 组件卸载即全丢」；`overscanPx=1200` 固定像素对整页 HTML 状态栏这类超高卡片覆盖不足，
单条高度就可能吃掉整个缓冲区，导致相邻条目频繁挂载/卸载抖动。

**键纪律（唯一直风险）**：键含**渲染输入本身**（文本 + `renderHtml` 开关 + `scriptHash` + `depth` +
`scopeId` + `charName`）而非消息 id，否则「内容变了但 id 未变」会命中陈旧条目。
**注**：计划文档写的键形态 `` `${scopeId}|${scriptHash}|${depth}|${text}` `` 与代码不符，
实际 `ChatWindow.vue:83` 用 `\n` 分隔——本轮以代码为准并沿用该口径。

**验证证据**

- 新增 `renderCache.test.ts`（7 例）+ `ChatMessageItem.renderCache.test.ts`（7 例）+
  `useVirtualMessages.test.ts` 追加 6 例；`npm test -w web` → 91 文件 / 896 用例全绿。
- **判别力实证**：「卸载后重新挂载同一内容零重算」「scoped 分支零重算」「50 条来回滚动两遍第二遍零重算」
  三例在接入缓存前**实测失败**（分别 2 次/2 次/100 次而非 1 次/1 次/50 次），接入后转绿。
- `npm run typecheck -w web`、`check-frontend-lint.mjs`（过程中曾因测试内 `as unknown as` 触发 +1，
  已改为真实 `RegexScript` 类型，回到基线 70）、`check-arch.mjs`、`npm run build -w web` 均通过。

### 三、P-12 前端体积预算门禁 + 性能门禁可见性（提交 `13e47d6`）

**改了什么**：新增 `tools/check-bundle.mjs`（纯 Node 零依赖，体例对齐 `check-frontend-lint.mjs`：
基线常量 + ratchet 只降不升 + `--verbose`）；断言四件事 —— ① `index.html` 的 modulepreload
**不含** `modal-*`（P-8 的固化护栏）；② 首屏集合 gzip 总量；③ 各 chunk gzip 体积（按**去哈希名**索引）；
④ 全部资产 gzip 总量。`check-all.ps1` 在 `vite build` 之后、同一 `if (-not $Quick)` 块内接入
`web: bundle budget`；并为性能门禁加 `else` 分支，收尾显式打印「未运行 + 如何开启 + 未测 ≠ 通过」。

**为何这么改**：`check-all` 跑 `vite build` 只断言「构建成功」，不看产物大小 ——
chunk 划分被无意改坏（依赖挪动、manualChunks 调整、新引重库）时构建依然全绿，只有用户能感觉到首屏变慢。
P-8/P-9 刚动过 chunk 划分与渲染路径，此时固化护栏成本最低。性能门禁此前默认关闭且**无任何提示**，
收尾只打印「全部通过」，容易被误读为「性能也过了」。

**验证证据（正向 + 五组反向，反向验证是本项的核心价值）**

| 场景 | 结果 |
|---|---|
| 正向：`node tools/check-bundle.mjs` | exit 0；首屏 261,293 / 预算 288,000；全部资产 369,533 / 预算 407,000 |
| 反向 A：把 `modal-*` 加回预载 | exit 1，报「首屏预载了弹窗 chunk」 |
| 反向 B：撑大单个 chunk（不可压缩随机字节）| exit 1，报「chunk 超预算」 |
| 反向 C：`web/dist/assets` 缺失 | exit 1，fail-closed 提示 |
| 反向 D：8 个小 chunk 各涨、单项均不超预算 | exit 1，报「全部资产超预算」 |
| 反向 E：多个首屏 chunk 小幅上涨、单项均不超 | exit 1，「首屏合计超预算」与单项同时报出 |

**反向验证过程中发现并修复了门禁自身的缺陷（如实记录）**：首屏总量与全部资产总量最初**只打印不判定**，
即两条断言形同虚设 —— 是反向 D/E 才暴露出来，已改为入失败列表。这正是负向验证的意义。

- 接线实测：`check-all.ps1 -SkipRust` → 11 阶段全 OK（含 `web: bundle budget`），
  收尾正确打印「性能门禁:未运行」。
- 另修正 `MAINTENANCE.md:149` 链式清单的两处过时表述（补 `docs`/`count`/`bundle budget` 三阶段；
  「npm audit(警告)」→ 硬门禁，实现自 2026-09-13 起已是硬门禁）。

**一并修正（P-9 的漏检，如实记录）**：本次 `check-all` 抓到 P-9 提交的一处门禁红灯 ——
新增根文件 `web/src/renderCache.ts` 未在 `tools/arch-layers.json` 登记代际（违反规则 I 与 J）。

### 四、P-13 `-j 2` 并发限制解除实验（提交 `2aa7179`）

**结论：上限由 2 放宽到 8；历史故障未复现。** 完整矩阵与适用边界见 `docs/经验.md` 条目 29。

| 2 | **冷 target 全并行（16 jobs）** | exit 0，1157 passed / 0 failed | 无 | 9m57s |

  `os error 1455`/`页面文件太小`/`E0786`/`internal compiler error` → **五份日志全部零命中**。

### 五、P-11 `derived_json` 派生列（提交 `ef2dfe5`，本批唯一有数据影响）

**改了什么**：`characters` 表尾加 `derived_json TEXT NOT NULL DEFAULT '{}'`；
新增 `parsing/character_derived.rs`（L1 纯函数，`compute_derived_json` 为派生字段的**单一计算源**）；
`migration/ddl.rs` 新增 `ensure_characters_derived_json_column` 与事务外的幂等回填
`ensure_characters_derived_backfill`；升级链与 `merge.rs` 两侧各接一次；
`character_service.rs` 的行映射改为「优先读列，列空/非法则回退解析 `data_raw`」、`list()` 改 `prepare_cached`、
`reflatten_v3_cards` 由 N+1 改单次全表扫描；三个写点（seed/upload/update）与收口
`character_data::update_data_raw`、旁路 `user_script_service::write_character_raw` 均同步写列。

**为何这么改**：`row_to_character` 此前**无论 `with_data_raw` 真假都做整份 `serde_json::from_str`**，
只为取 6 个派生字段，列表成本是 O(卡数 × 卡体积)；`reflatten_v3_cards` 的 N+1 由
`seed_default_character` 在**每次启动**触发。

**关键设计决策：该列是缓存而非事实源。** 读取侧在列为空/非法时回退解析 `data_raw`，于是：
回填从「正确性必需」降为「性能必需」；旧库未回填、旁路未同步都不会显示错数据（最差只是慢）；
**不动 `SCHEMA_VERSION`**（保持 1，与 `finished_at`/`pinned`/`task_mode` 三处先例一致）⟹
旧版 exe 打开加列后的库是安全的，**回滚不必依赖备份恢复**。

**验证证据**

  **回退证明**（列为 `'{}'`/非法 JSON 而 `data_raw` 合法 → 列表仍正确）、**旁路防护**（旧字段迁移直写后列已刷新）。

**为何这么改（根因：两层缺陷叠加，后者被前者掩盖）**

- **第一层（类找不到）**:`exec/android.rs` 经 `call_string_static(EXEC_CLASS, "detectTier")` 调 Kotlin `ShellExecutorBridge`,

- **审查修正（同批第二次提交）**：① 聊天侧展开 **id 唯一化**；② 校验分层（保存全库 / 执行只查入口
  可达链）；③ 子图**降级信号**不再被吞（→ `partial` + plan 行标注，标注不污染下游）；
  ④ 前端深度警示补**祖先层数**、停用步骤/停用流程口径、被引用流程结构检查；
  ⑤ `normalizeStepAction` 切 reflect 时清 `sub_flow_id`；⑥ `remove` 只看启用步骤的引用；
  ⑦ 挂载节点不再被误标「(内部规划)」；⑧ `MAINTENANCE.md` 计数门禁转绿。

### 为何这么改

- **子图取「引用流程 id」而非内联嵌套**：内联嵌套要在列表与画布各做一套嵌套编辑 UI，成本远超本批；
  引用形态与批次 7 的「子执行 + 深度守卫 + 记账」原语同构，且静态引用的环与深度**能在保存期完全判定**
  （裁定 18 差异 1）。
- **记账 phase 用点号路径、不用冒号**：前端流式缓冲 key 是 `${phase}:${step_index ?? ''}` 且按
  **首个冒号**切分（`CallTracePanel.vue` / `stores/task.ts` 的 `liveKey`）——phase 含冒号会让 phase 与
  步骤号解析错位、嵌套调用的缓冲互相覆盖。点号路径保持零 schema 改动且能读出挂载来源（裁定 18 差异 2）。
- **挂载节点不记 usage、子图不写 plan**：`/calls` 各行求和 == 详情 `usage_total` 是既有不变量，
  父子两层各记一次就破；plan 是外层流程的节点列表（`TaskStep` 只有 4 字段、无 `node_id`，
  与 IFW-5 同因）。
- **聊天侧展开必须重写 id（P1）**：展开只清 `inputs`、加名字前缀时，**同一子流程被两处挂载**或
  **父子流程撞 id**（「复制流程」原样保留 step id）会产出重复 id 的扁平列表，而该列表随后还要过
  `make_custom_plan` → `resolve_graph`（`effective_inputs` 以「步骤 id 重复」拒绝）→
  **任务侧照常跑完、聊天侧 400**，且错误文案看不出与子流程有关——违反 6a 立下的「同一份已保存流程
  两侧行为必须一致」。修法：子层前缀 `s{挂载下标}/`（顶层空串，顶层 id 逐字节不变）+ 返回前自检
  `resolve_graph` 并把失败包成点名重复 id 的中文错误。
- **校验分层（P2）**：原执行期 `validate` 也是全库口径 → 库里任一**无关**流程的脏引用
  （手改 `data/agent_flows.json`、外部导入）会让**所有** custom 任务与聊天预览起不来，错误还指向
  那个无关流程。改为「保存期全库、执行期只查入口可达链」，环/深度另由运行期调用链守卫兜底。
- **子图降级不能被吞（P2）**：子图内有节点失败但成果仍选得出时 `run_sub_flow` 返回 `Ok`，
  外层把挂载节点标 `done`、任务报 `done`——与「同层普通节点失败 → `partial`」不自洽，主界面也没有
  任何降级提示。故把「本节点是否降级完成」作为 `NodeOutcome.degraded` 带回本层汇总，
  标注只进 plan 展示、不进 `outputs`（避免污染下游提示词）。
- **前端提示必须与保存期校验同口径**：① 深度判定原来只按「本流程是根」算向下层数，
  而本流程自身可能已被祖先挂了两层 → 用户一条警示都看不到、保存却被拒（假阴性），
  故新增 `flowAncestorDepth` 按**反向边**算祖先跳数；② 停用步骤/停用流程原先一律报「保存会被拒绝」
  （假阳性，后端对它们直接放行），故给 `stepSubFlowWarnings` 补 `enabled`/`flowEnabled` 两个开关，
  并保留**后端确实会拒**的那几类（全库校验不跳过未启用流程）；③ 「点一下动作下拉变反思」会让
  流程立刻不可保存且折叠态无任何标记，故 `normalizeStepAction` 一并清 `sub_flow_id`。

### 为何这么改

- **超时语义取「单次调用」而非「节点整体预算」**：与既有 `TASK_TOOL_LOOP_CALL_TIMEOUT` 同粒度，宽松档
  工具循环**逐轮**各按该值计；若写成 `min(覆盖, 缺省)`，「给慢节点放宽」这条诉求会被静默吃掉。
- **重试只认空产出，且重试必带预算翻倍**：硬错误重试只会把成本成倍地耗在同一个坏引用上，还会与超时
  语义互相掩盖；而空产出最常见的成因是推理吃光输出预算，只重试不加预算等于把同一次失败原样重放。
- **新增字段一律加性、缺省一律等于现状**：`PlanStep` / `TaskRecord` 的新字段全部
  `#[serde(default, skip_serializing_if = "Option::is_none")]`（`None` 整键省略）；三个设置项的默认值逐项
  等于引入前的行为（2 / 8 / 不裁剪）。「节点默认上下文」的 0 是刻意的——按「默认套全局上限」落地会让
  **所有既有流程**突然受约束（裁定 26 口径 2 的顾虑），故把「给任务侧加溢出保护」变成显式选择。
- **常量退居默认值、设置项为真源**：运行期闸门读 `TaskRunContext.settings`（任务开跑时的设置快照），
  中途改设置不影响本轮；测试仍以常量为基准。
- **任务级连接只设三处收口点**（而非在每个调用点各写一遍）：规划 / 步骤 / 汇总 / team / legacy 五条纯生成
  路径走 `generate_text_timed` 的内部回退，工具循环走 `TaskRunContext.connection_id` 下传，
  plan / team / followup 走 `AgentLoopCall.connection_id`。
- **任务是本机的，故创建期即校验**：流程库要跨机搬运（引用可能指向别的机器），校验只能推迟到运行期；
  任务不会跨机，创建期 400 点名连接比让用户跑一半才发现更友好，运行期再按 5b 口径兜底明确报错。
- **改绑撤销旧口径、导入覆盖按份替换**：两者的共同纪律是**不做静默动作**——改绑必须显式全量替换并二次
  确认「替换快照」；覆盖必须显式勾选，未知 `on_conflict` 值直接 400，且都不删库里其它流程。

## <a id="2026-09-26-taskmode-d2"></a>2026-09-26 任务模式实测缺陷修复 · 提交 2（部分成果兜底 D2）

> 来源：`docs/plans/TASK-MODE-FIX-PLAN.md` §4 与 §10 口径裁定（临时执行稿，收口时删除）。
> 本批只做提交 2；提交 3（步骤墙钟预算默认 1200s / 语义熔断任务侧钳制 / 编码纪律提示段 /
> `finish=length` 可操作报错 / 任务级空闲自愈 / 探针移植）留待下一轮。

**改了什么（条目化）**

- **新增确定性拼装器（单一出处）**：`services/task_core/assemble.rs`——
  `assemble_from_plan(&[TaskStep]) -> Option<String>` 只收「`status == Done` 且 result 非空」
  的步骤，按 plan 顺序拼 `## 步骤名` + 正文（名称按空白归一，防在段内制造假标题行），
  有失败步时另起一行 `> 未完成的步骤:…`；**无任何可拼装内容返回 `None`**。不调 LLM、不读库。
  `fallback_terminal(plan, reason)` 一处判定：能拼出成果 → `Complete{status: partial,
  result: 拼装文本, error: Some(原因)}`，拼不出才是 `Failed{error: Some(原因)}`。
- **四模式失败降级**：legacy / plan 的汇总调用失败、team 的审计 / 终审 / 汇总调用失败与
  汇总空产出（含首轮汇总同参数重试仍空）、custom 的 `run_graph` 失败与「未产出任何成果」
  全部改走 `fallback_terminal`；team 的「全部主 agent 无产出 / 补做后仍无产出」同经该判定
  （此时 plan 无已完成步骤，行为与旧实现逐字一致）。**取消分支仍返回 `Err`**，交由引擎按
  `ended` 收尾——避免把「已停止」误报成 partial。
- **终态兜底落库**：`task_service::executor::salvage_partial_result`（读库 → 拼装 →
  `db::set_result_only`）在 `finalize_run` 写终态前调用；`stop()` 也在置 `ended` **之前**
  调用同一个函数——两条路径都不丢成果，且「已停止」一出现就带成果（执行器随后收尾因
  result 非空自动跳过，幂等）。`set_result_only` 只 `UPDATE result`，不动 status/error，
  写成功发既有 `kind=status` 事件（不新增事件 kind）。
- **重启中断兜底**：`recover_orphan_tasks` 把 running/planning 置 ended 后，对 plan 中有
  已完成步骤的行补写拼装成果（`WHERE result = ''` 保证不覆盖既有成果）；既有单测扩了三态
  （有产出 → 补写 / 无产出 → 保持空 / 已有 result → 不覆盖）。
- **批准即失效预览**（真模型实测追加）：`approve` 在置 planning 时 `db::clear_result` 清空
  planned 态写入的「待批准计划清单」result（只清 result 列、不发事件——紧随其后的
  status/plan 写入各自发事件）。**起因**：真模型 plan/写作 实测里某步已完成 560 字，
  `task.result` 却仍是计划清单——续跑期间那条 result 一直非空，兜底的「result 为空才补写」
  判据整条跳过，前端成果卡就把**计划**当成「已完成部分的成果」展示了。清空后：续跑成功由

**为何这么改**（缺陷机理，实测证据见 `docs/plans/TASK-MODE-FIX-PLAN.md` §1 D2）

「已完成的工作被丢弃」是三层各让一步的结果，缺一层都不成灾：①**类型层**——终态
`TaskTerminal::Failed` 只带 `error`，没有承载部分成果的字段，执行器想交也交不出来；
②**落库层**——`finalize_run` 的 error/ended 分支只写 `status`/`error`，**从不碰 `result`**，
即便 plan 里每步产出都在也没人写进成果列；③**展示层**——前端成果卡门控是
`status ∈ {done, partial}`，前两层修好也不渲染。修复的纪律是「判定只写一处」（拼装器 +
`fallback_terminal` + `set_result_only` 三件套，四模式与三条兜底路径共用）与
「不伪造成果」（没有任何「已完成且产出非空」的步骤时，终态与空 result 与旧行为逐字一致，
正反两面各有一条用例钉住）。

## <a id="2026-09-26-taskmode-d3"></a>2026-09-26 任务模式实测缺陷修复 · 提交 3（能收敛 D3/D6/D7 + 探针）

**改了什么（条目化）**

- **步骤墙钟预算**（`GenerationParams.step_budget` + 纯函数 `executor::step_budget_reached`）：
  单次 `run_tool_loop` 的墙钟上限，闸门置于 **token 预算闸门之后、`last_round` 判定之前**

- 推送是**备份与回滚粒度**的前提；`docs/展望.md` OA-A 的触发条件（「仓库配置远端并推送 GitHub」）

- **平台分支同步（`main` → 平台分支的 `rebase`）刻意不在本批**：它改写平台分支历史，
  与「建仓首推」混在一批会让回滚失去粒度。

  属**另一批次**的测试工作。
