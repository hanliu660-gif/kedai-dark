## <a id="2026-10-07-cu1-safety"></a>2026-10-07 电脑操作安全前提（CU-1 收窄版：屏幕/输入类提级 + 急停 + 操作审计）

**背景**：CU 执行稿（`plans/COMPUTER-USE-PLAN.md`，原稿已并入 `计划.md`）的「提交 1 安全前提」
按 2026-10-06 用户三条裁定收窄后落地：把「已经打开的键鼠/屏幕通道」收回到可授权状态，
并给既有 `screenshot` 读屏能力补上急停与操作审计。**本批不含任何新 GUI 能力**（纯收紧 + 基建）。

**提交 1（`a4952d4`）——屏幕/输入类命令提级**

- `CommandRisk` 新增第五级 `ScreenInput`（Android 设备控制原语 `input`/`screencap`/`uiautomator`/
  `dumpsys`/`ime`）：Ord 置最右保证多段串联取最高危时胜出；`requires_explicit_confirm()` 纳入 →
  复用 `permissions.rs` 既有**命令级硬门**（判定顺序不动），四档（Strict/Loose/Bypass/任务白名单）
  与工具级显式授权一律不自动放行；硬门理由按类别生成——屏幕/输入类单列文案
  「会代替用户操作真实设备/读取屏幕，不受任何授权豁免；任务模式不支持」，Destructive/Admin 文案逐字节不变。
- 缺口实证（改前）：这五条命令不在任何词表 → 未识别兜底 `Sensitive` → 任务白名单档
  （`custom_authorized`）与放行档**自动放行**（等价键鼠注入/读屏通道无人值守下已开）。
- **桌面侧 powershell/pwsh 本轮不纳入**（用户裁定）：通用解释器静态清单必然不完备
  （python/node/mshta/wscript 同类可达）且误伤 Windows 常规开发工作流；留待 CU 提交 3/4 的结构化
  工具族 + 能力总闸。诚实边界与 `遗留.md` T2 同口径：**词表不是安全边界**（追注已登记）。
- 同步消费方：前端 `CommandRiskLevel` 加 `'screen_input'`、审计面板 `RISK_LABEL` 与风险筛选加
  「屏幕/输入」、`api/exec.rs` 的 `AuditQuery.risk` 注释补值。
- 测试：先写失败测试（实测输出 `left: Sensitive / right: ScreenInput`）再实现；新增
  `screen_input_commands_are_escalated` / `chained_screen_input_takes_highest` /
  `screen_input_commands_never_auto_allowed_in_any_mode`（四档全拒 + 任务白名单 + 工具级授权）
  与 `tool_policy` 词汇断言；既有 Sensitive 语义与三条硬门回归逐条不变。

## <a id="2026-10-07-comment-audit"></a>2026-10-07 注释质量审计与定点清理（Forbric 式问题排查：3 处错位 + 复述式残留 30 余处；提交 `f11af52` + 本台账提交）

**背景**：用户以 Forbric（第三方 Minecraft mod loader）被批评的两类注释问题为标尺，要求排查本仓
是否存在同款问题——① 注释只对源码做「逐句翻译/复述」（删掉零信息量）；② 注释块与代码块失去对应
（乱插/错位）。全仓抽样审计（后端约 40 文件、前端约 30 文件精读 + 全库 grep）结论：**不存在系统性
Forbric 式问题**（注释主脉是 why / 约束 / 事故编号引用，复述式占比 <3%）；据此只做定点清理，
不动注释文化本身。

**改了什么（A/B/C 三类定点清理 + D 类复核不修；全部只动注释文本，零行为改动）**

- **A 类·注释错位 3 处（真缺陷）**：`src-tauri/src/lib.rs` 的「应用入口 / `mobile_entry_point` /
  Android 缺属性启动即闪退」整段文档（原 112-116 行）从 `fallback_app_data_dir()` 移回其真正主人
  `pub fn run()`；`services/mod.rs` 两处模块声明注释分别移回 `native_bridge_android` 与 `undo_service`。
- **B 类·轻微错位 3 处**：`api/json_body.rs` 文件头注释被历史 rustfmt import 重排挤进 `use` 块——
  移回文件首并把 `use crate::api::WithStatus;` 归回 import 组（该文件至此恢复 fmt 可重排的规范形态，
  `cargo fmt` 复核稳定）；`web/src/stores/chat.ts` 行尾注释归位到其描述的 `reduceSseEvent` 调用上方；
  `ChatMessageItem.vue` 删除「原独立函数 renderText() 随之移除」过程叙述残留。
- **C 类·复述式 / 纯标签清理 30 余处**：后端 3 处（`agents/engine/util.rs` 删 `/// 检查中断`；
  `lib.rs` 两个测试 builder 的文档由同义复述改为「与 `build_test_app` 的差异 + 隔离语义」）；前端
  `api/{characters,worldbooks,plugins,skills}.ts` 四个文件头由「复述文件名」补成「端点清单 + 后端
  契约文件路径」（对齐同目录 `executors.ts` 体例）；`Sidebar.vue`(3) / `stores/chat.ts`(1) /
  `mvu/parser.ts`(1) 纯复述 5 处；模板分区纯标签 15 处（`ScriptsModal` 5 / `AudioPlayer` 3 /
  `AgentPanel` 7）；`tests/api_character_session.rs` 纯动作标签 4 处。
- **D 类·复核后明确不修（结论入档）**：三组「模板句」（纯代码移动 28 处 / DB 并发改造 20 处 /
  设置快照括注 17+ 处）经逐行核对，每处都带各自的站点信息（拆自哪个文件、哪次并发改造、锁在何处
  释放），属 `// SAFETY:` 式逐站点注释约定；use/import 块内注释（约 7 处）是 Rust 标注特定 import
  的标准形态；「注释偏长」的高密度文件（`utils/win.rs` 92%、`utils/blocking.rs` 42%）恰是全仓
  信息密度最高处——**均不构成 Forbric 式问题，不做瘦身**：本仓注释的事故编号引用链价值高于扫描成本。

**为何这么改**：修错位是消除真实误读（最典型的一处：读 `fallback_app_data_dir` 者会先看到
「Android 启动即闪退」而真正需要该警告的 `run()` 反而无文档）；清复述是执行本次审计的结论；
对承重注释明确不修，是防止「为整齐而删信息」。**本批不新增任何注释质量门禁**——审计未发现系统性

### 一、插件机制（提交 `2f92684`）

- **reload 增删同步（缺口 1）**：`register_plugins` → `sync_plugins`（**差集注销 + 注册三查**）——
  启动装配 / reload / upload / delete 四入口共用一条路径；批内跨文件重名**先到者生效、后到者进
  errors**（不覆盖）；reload 响应增 `removed`；`ToolRegistry` 增 `names_by_origin`（排序确定）。
- **加载期脚本校验（缺口 2）**：新增 `plugins::validate_script`（纯解析、不执行；与求值器共享语句
  切分与配平词法助手，防两套语法漂移），`parse_file` 调用——upload/reload 即报语法错误。
- **求值器 v2（裁定 3）**：语句序列（中间变量 `ident = 表达式` + 末句 `return`/`result =`；`;`/换行
  分隔）、多级成员链（`args.user.name`）、下标 `[n]`、`+` 数值对算术否则**字符串拼接**、比较/逻辑/

  **显式报错**（含可用键/长度定位）；顺带修复「字面量拼接被当单一字符串」与「`&&` 与比较混用报错」
  两处旧问题。仍无 IO / 循环 / eval（白名单路线不变）。
- **API/UI 收口（缺口 4/5）**：`GET /api/plugins/tools` 只回插件来源、每项带 `origin`/`file`；
  PluginsModal 按来源文件分组、修两处文案漂移（「内置不在此列表」与引用不存在的

### 三、管理面与来源可见（提交 `3af0997`）

- **端点（新建 `api/mcp.rs`，路由进 `api/routes/misc.rs`，契约路由表同步过 `api-routes-covered`）**：
  `GET /api/mcp/servers`（状态列表；state 四值 `running/failed/stopped/disabled`，**运行实况优先于

## <a id="2026-10-26-build1"></a>2026-10-26 构建提速批（BUILD-1）：默认保留编译缓存 + release 改 thin LTO

**定位**：`dark` 派生分支上的本机工程改动（不为上游贡献，也不改变产品功能）。前置批
`2026-10-26-night1`（夜间模式）之后，千夏提出「每次编译慢了点，有提升空间吗」，本批只动构建链。

**改了什么**

- `build.ps1`：新增 `-Clean` 开关。**默认（不带）构建收尾不再删 `server-rs\target` 与
  `src-tauri\target`**，改为打印「[保留] 编译缓存留在 …」；只有 `-Clean` 才回到旧的整删口径。
  便携版调用相应改成 `if ($Clean) { build-portable.ps1 -NoWeb } else { … -NoWeb -KeepTarget }`。
- `tools/build-portable.ps1`：新增 `-KeepTarget` 开关，把打包后的清理段整段包进 `else` 分支
  ——此前光改 `build.ps1` 无效，真正删 target 的是这个脚本自己的收尾清理（:113-141）。
- `server-rs/Cargo.toml`、`src-tauri/Cargo.toml`：`[profile.release] lto = true` → `lto = "thin"`。
- `tools/perf-baseline.json` 的 `"build": "release (lto=true, strip=true)"` **故意不动**：那是历史
  实测口径，`perf-baseline.mjs` 不读该字段。

**为何这么改**

- 旧口径每次构建后整删 target，下次必然全量重编 500+ crate：实测一次成功构建固定 12m33s，其中
  后端 release 占 98.7%（前端 vite 6.4s、launcher 4.0s）。保留缓存后增量构建只重编

- 交付链不允许只换清理段：`build.ps1` 的清理块里还夹着「复制 `kedai-server.exe` 到 `dist\`」与
  写 `Kedai.exe.build.json` 指纹，`start.ps1` / launcher 靠它判两版同源。故只加开关、不动结构。
- thin LTO 把跨 crate 的 LTO 并行化，链接阶段变短；代价是产物字节变化（文件大一档）与理论上限
  性能略让位。千夏 2026-10-26 明确拍板：「只要速度快，文件大点没关系」。

## <a id="2026-10-29-carda"></a>2026-10-29 CARD-A 批：酒馆整页前端卡（HTML 界面卡）在 Kedai 内的渲染修复

**定位**：千夏导入的「圣像之下 RE v0.4.0-test」开场页在 Kedai 里显示成「一列列竖排单字」。
本批只修**渲染管线**（作用域化 / 白名单 / 容器宽度），脚本执行链路零改动——
变量引擎（MVU）与卡内 `import` 依赖不在本批范围（见「边界与未做」）。

**四张实测卡（`Z:\sb\bf`，PNG 卡按 tEXt/iTXt 解析后实测；共 13 段 ≥1000 字符的前端 replaceString）**

| 卡 | 开场 HTML | @media 源 | 修前 @media 出 | 修前死 `:root` |
|---|---|---|---|---|
| 圣像之下 RE | 734,604 字符整页文档 | 10 | **0** | 3 |
| 魔法少女的星庇岛逃离计划 | 47,476 字符（含状态栏界面） | 2 | **0** | 1 |
| 露出日记-0615 | 4 组片段（41,124 最大） | 6 | **0** | 1/1/1 |
| 性开放 | 21,710 / 22,158 状态栏两版 | 0 | 0 | 1/1 |

共性（13 段合计 22 个 `@media`）：**22/22 全灭**；7 段带 `:root` 且**全部**变成死选择器；5 段带
ESM `import`（沙箱直接整条跳过 ⇒ 变量引擎跑不起来）。

**根因（三条，各自独立可复现）**

1. **整页 HTML 走错渲染通道**：`ChatMessageItem.vue:276` 的 `renderMessageHtml()` 用
   `isRenderCodeBlock(text)`（`renderPanel.ts:6-9`，判 `'<html'` + `'<head'|'<body'`）决定是否交给
   渲染面板 iframe，而 `text` 取的是**正则替换前**的原文 —— 角色卡经 `regex_scripts` 注入的整页
   文档永远判不中，于是内联进气泡。
2. **`:root` 被作用域化成死选择器**：`cssSanitize.ts` 的 `scopeSelector()` 只把**前导** `html`/`body`
   重写成容器，`:root` 落到 `${attr} ${s}` 分支 → `[data-kd-scope="kx1"] :root{…}`，容器是 `div`，
   永不匹配 ⇒ 卡的全部设计令牌（`--sv-paper` 等）失效，转而继承 Kedai 的同名令牌
   （`styles/tokens.css:191 --sv-paper:#0f0f11`，与卡的 `--sv-paper` 撞名）⇒ 暗底暗字。
3. **整类 at-rule 被清洗丢弃**：`sanitizeScopedCss()` 的 `isAt` 分支只保留 `@keyframes`，其余
   at-rule 一律 `return ''` ⇒ `@media` / `@supports` / `@font-face` 全灭。卡的响应式断点是整页
   布局的一部分（940px 设计稿在 560px 气泡内靠 `@media` 兜底），丢掉即塌。
   还有第四条（同源）：`<'*'`> 白名单没有 `hidden`，且 sanitize-html 会删「值为空且属
   `nonBooleanAttributes`」的属性 —— 卡里「默认隐藏、脚本就绪后再显示」的分层会同时露出。

**改了什么**

- `web/src/cssSanitize.ts` `sanitizeScopedCss()`：`isAt` 分支新增两条放行——
  `@media|@supports|@container|@layer|@scope` 递归清洗块体后保留；`@font-face` 走声明级清洗后保留；
  `@import`/`@charset`/`@page` 仍丢弃。条件规则内部仍逐条过 `sanitizeCssDeclarations`，
  `expression()`/`javascript:`/非白名单 `url()` 不能借 `@media` 混进来。
- `web/src/cssSanitize.ts` `scopeSelector()`：把 `:root`/`html`/`body` 一并视为**文档根**并折叠到
  作用域容器本体（最多 4 跳，`html body .x` 亦折叠），产出 `[data-kd-scope="k"]{…}` /
  `[data-kd-scope="k"] .x{…}`；`:root[data-theme='dark']` 这类附带选择器原样保留在容器上。
- `web/src/render.ts` `sanitizeVisibleHtml()`：`allowedTags` 增补语义容器
  `main/section/article/nav/header/footer/aside/figure/figcaption/mark/cite/q/time/abbr/kbd/samp/var`
  （整页卡的骨架依赖它们命中卡自己的 `main.sv-stage`/`nav.sv-stepper` 规则）；
  `allowedAttributes['*']` 增 `hidden`，并显式声明 `allowedEmptyAttributes`
  （`hidden/checked/disabled/selected/multiple`）——sanitize-html 2.17 起支持该选项，
  但 `@types/sanitize-html` 2.16.1 还没声明，故用交叉类型
  `SanitizeVisibleOptions = NonNullable<Parameters<typeof sanitizeHtml>[1]> & { allowedEmptyAttributes: string[] }` 补齐，
  避免 `as never`/`as unknown as`（类型 ratchet 只降不升）。
- `web/src/styles/shell.css`：`:has([data-kd-scope])` 气泡上限 92% → **100%**；

## <a id="2026-10-29-b1s"></a>2026-10-29-b1s 折叠面板下方那一大片空白——内容高度只量 body

  与 `scheduleHeight()` 都改为用它。
- `web/src/composables/useResourceFrames.ts`：高度下限 120 → **48**（收起态一行标题也能贴住），
  上限仍 4000。
- 测试 +2（`useResourceFrames.test.ts`：60px 被采纳、12px 被忽略、9000 裁剪到 4000）；
  `server-rs/tests/api_misc_assets.rs` 增一条断言（模板必须含 `contentHeight`）。

**实测（隔离实例，1440×900）**：同一段对话的 6 个整页卡窗口高度

### 2026-10-29 卡级脚本沙箱补丁二（悬浮球三条：吃点击 / 关了回不来 / 卡死）

上一批让「悬浮球-0613」跑起来之后，用户实跑立刻撞到三个问题（`C:/DSH/APP` 笔记里叫「三条」）：

1. **球一出现，页面别的按钮全点不动**（聊天区、顶栏、输入框、左栏都没反应）；
2. **点「关闭」后球消失，再也回不来**，只能刷新页面；
3. **页面会卡死**（拖动/操作悬浮球期间整页发涩）。

**根因（三条，全部实测确认）**

1. **`pointer-events` 被宿主无条件改写**：卡作者给悬浮层的挂载根写了
   `{position:'fixed', inset:0, 'z-index':9999, 'pointer-events':'none'}`（酒馆惯例：容器铺满屏幕
   但不吃点击，只有里面的球/面板可点）。`web/src/sandbox/dom-rpc.ts` 的 `markInjected()` 为了
   「注入节点可点」对**父是覆层根**的节点无条件 `el.style.pointerEvents='auto'` ⇒ 一个铺满屏幕、
   `z-index:9999` 的层把整页点击全吃掉。**这是上一批自己引入的回归。**
2. **宿主没有脚本按钮栏**：卡的「关闭」只收面板并把球 `display:none`，恢复入口是
   `appendInexistentScriptButtons([{name:'悬浮窗开关'}])` + `eventOn(getButtonEvent(name))`，即
   SillyTavern 的**脚本按钮栏**。沙箱只把按钮记在内存（`getScriptButtons()`）就完了，没有任何渲染。
3. **事件洪泛 + 每包全量镜像**：拖动时每个 `mousemove` 都走「宿主 postMessage → 沙箱回调 → 一批 DOM op
   → 回包带全量状态镜像（选择器扫描 + 控件扫描 + 所有 `[data-kd-el]` 的 rect）」，逐像素往返把主线程排满。

**改了什么**

1. `web/src/sandbox/dom-rpc.ts` `markInjected()`：只在作者**没写** `pointer-events` 时才补 `auto`，
   显式写了 `none` 的层绝不覆盖。
2. 新增**宿主侧脚本按钮栏**链路（协议 → 沙箱 → 宿主 → 界面）：
   - `web/src/sandbox/protocol.ts`：`SandboxScriptButton { name; visible? }`；`SandboxRequest.type` 增
     `'script-buttons'`；`SandboxExecutionContext` 增 `onScriptButtons?`（沙箱登记后上送全量列表）与
     `sendToSandbox?`（执行器写入的宿主→沙箱投递入口）。
   - `web/src/sandbox/boot-script.ts`：`__kdPublishScriptButtons()` 在
     `appendInexistentScriptButtons`/`replaceScriptButtons` 之后上送；`script-button-click` 消息以
     `getButtonEvent(name)` 广播（对齐酒馆 `getButtonId = scriptId + '_' + hash(name)`）。
   - `web/src/sandbox/iframe-lifecycle.ts`：建好 iframe 后写 `context.sendToSandbox`；message handler 收
     `script-buttons` 转 `onScriptButtons`。
   - `web/src/cardScriptHost.ts`：`onScriptButtons` 透传 + 导出 `clickCardScriptButton(name)`。
   - `web/src/components/ChatWindow.vue`：`scriptButtons` ref + 流式 `.sv-script-bar` 按钮栏（`role="toolbar"`，
     令牌化样式，不用 absolute 定位以免再叠一层挡点击）。
3. 新增 `web/src/sandbox/host-events.ts`（**宿主侧**事件合帧）：`postSandboxEvent()` 只对
   `mousemove/pointermove/touchmove/scroll/wheel/drag/dragover` 按 `(jqId, 事件名)` 合并成「一帧只留最新」，
   其余事件即时投递；`requestAnimationFrame` 不可用时退化 `setTimeout(16)`。`dom-rpc.ts` 两处 jq-event
   发送点与 `draggable.ts` 的 `postEvent()` 全部改走它。
4. **动画效果回调不再丢失**：`boot-script.ts` 新增 `__kdAnimArgs`/`__kdAnimRun`，把
   `fadeIn(ms, cb)` / `fadeOut(ms, cb)` / `hide/show/toggle/slideDown/slideUp(cb)` 里的函数按
   `setTimeout(cb, min(ms,1000))` 执行一次（display 立即置位的语义不变）；游离元素集合与选择器集合两处都接。
   卡的「关闭」正是 `s.stop(true,true).fadeOut(120, function(){ 把球 display 显示回来 })`。

**为什么这么改（踩过的坑，别再走一遍）**

- **事件合帧绝不能放在沙箱侧**：沙箱 iframe 是 `display:none`、0×0 的隐藏文档，其 realm 内
  `requestAnimationFrame` **永不回调**（实测 1.5 s 只跑 1 帧；`requestAnimationFrame` 包 Promise →
  `TIMEOUT_1000ms`，同窗口 `setTimeout` 正常）。第一版把合帧写在沙箱里，结果所有 `jq-event` 永久积压、
  点球/点 tab/点关闭**全静默无反应且零报错**，排查代价极高。正控实验（事件发生前把沙箱 `rAF` 换成
  `setTimeout(cb,0)`）立刻恢复正常，才定案。现在沙箱侧是**同步派发**，有一条防回归用例守着
  （「连发三条 mousemove 全部按序到达」）。
- 按钮栏用普通 flex 行（`<ChatInput />` 之前）而不是绝对定位浮层，避免又做出一层吃点击的层。
